# 第 1 部分：逐句反推 28 题（每题完整参考回答）

## A. 简历要点①：流式 + 工具调用兼容性

### A1. 为什么不用真流式，改成阻塞调用加分块回放？

🎤 **我本来做的是真流式，上线发现 Spring AI 的流式接口和工具调用组合使用时，在 DashScope/Qwen 上有已知缺陷——跨流式分片聚合工具调用参数失败，直接抛异常断流，官方 issue 里确认了这个问题，官方给的临时方案就是改用非流式调用。所以我改成"伪流式"：后端一次性拿到完整回答，然后按三十字一块切片，定时往前端推，用户的观感和打字机完全一样。这里的关键是想清楚用户要什么——用户要的是"答案逐字出现"的感知，中间是不是真空流没人看得见。同时我留了升级开关，官方修复后只改一个方法就能切回真流式，对外接口和前端零改动。遇到基础设施 bug，先用最小改动保住用户体验，同时给修复路径留门。**

「追问」issue 号记得吗？→ spring-ai 主仓 #4790、spring-ai-alibaba #1025，都记录在代码注释里。能脱口而出 issue 号是"真踩过坑"的硬证据。
「追问」真流式首字延迟低，不想要吗？→ 想要，但功能可用性优先；而且我的链路中间要调工具，工具执行本身占时间，真流式的首字优势会被吃掉一部分，伪流式的体验损失更小。

### A2. Flux.defer / Schedulers.boundedElastic 是什么？为什么用？

🎤 **这两个词来自刚才那个流式兼容方案。我改成阻塞调用一次拿全量结果——但阻塞调用绝不能放在响应式的事件循环线程上，会把整个服务卡死，所以用 boundedElastic 调度器把阻塞调用挪到专门的弹性线程池里隔离执行；Flux.defer 则保证每次订阅都独立执行这段逻辑、拿到独立的流，不会出现多个订阅者共享同一次结果的错乱。拿到结果后切片定时推送，前端看起来就是流式。三个词各司其职：阻塞调用解决兼容性，boundedElastic 解决阻塞任务不能占事件循环线程，切片回放保住流式体验。**

「追问」boundedElastic 和普通线程池区别？→ 它是响应式框架专门为包装阻塞任务设计的调度器，线程数按 CPU 倍数弹性伸缩并带队列缓冲，设计目的就是"隔离阻塞、保护非阻塞线程"。

### A3. 为什么选 SSE 不选 WebSocket？

🎤 **本质是单向和双向的区别。AI 对话场景里客户端只发一次请求、之后全是服务端往下推，天然单向，SSE 完全够用，而且有三个工程优势：它基于普通 HTTP，不需要协议升级；经过 Nginx、网关、代理的兼容性远好于 WebSocket；断线重连浏览器原生支持。WebSocket 是给双向实时场景准备的——协作编辑、在线游戏、弹幕。我的场景按需选型，不上重型方案。**

「追问」前端怎么消费 SSE 的？→ 有个细节：浏览器原生的 EventSource 只能发 GET 请求、带不了鉴权头，所以前端用 fetch 拿到流手动逐块读取，既支持 POST 又能带 token。

### A4. Function Calling 怎么实现的？有哪些工具？

🎤 **基于 Spring AI 的工具机制：我把后端能力封装成五个带描述注解的工具方法，模型在对话中自主决定调不调、调哪个、传什么参数，框架负责执行后把结果回填给模型继续生成。五个工具是：附近地点推荐——按半径做地理围栏再语义排序，这是核心；名称关键词查找——用户明确指名某地时用；路线规划——问"怎么走、多远、多久"时用；类别列表——用户表述模糊时给他选项；还有用户偏好查询——按用户历史收藏习惯做个性化。有一个安全细节：涉及用户身份的工具，身份不是模型填的，是服务端注入的，模型看不见也改不了——这就引到身份隔离那道防线了。**

「追问」工具结果怎么保证不失真？→ 系统提示词强制要求模型引用地点数量和距离时必须与工具返回完全一致，再加模型评测里专门有"依据性"指标查它有没有编造。

## B. 简历要点②：三段式空间约束 RAG

### B1. 三段式空间约束怎么工作？为什么三段？

🎤 **用户问"附近适合带娃的地方"，我分三步：先画方框、再量距离、最后比语义。第一步以用户位置为圆心按半径画一个外接方框，数据库先把框外的全部排除——方框查询便宜，走普通索引就行。第二步框的四角其实超出半径，用球面距离公式精确算一遍，把真圆外面的剔掉。第三步剩下的少量候选才做向量语义排序，取最相关的几个。核心思想是"先便宜后昂贵"：语义计算是最贵的一步，我把它压到最后、只对几十个候选做，而不是对全库做。这也是我这套和通用 RAG 最大的区别——先问你在哪，再谈像不像。**

「追问」为什么不能纯语义检索？→ 全局向量检索回答的是"全库谁最像"，但"附近"是硬约束不是偏好，纯语义会把三公里外语义最像的排到前面，地图场景不可接受。

### B2. 为什么不直接用 PostGIS 的空间函数（比如 ST_DWithin）？

🎤 **功能上等价，都是先空间后语义，我用的是另一条工程路径。ST_DWithin 要求地理类型列和 GiST 空间索引，而我的地点表本来就有经纬度数值列和地图模块在用的范围查询——我直接复用这套既有查询和索引做边界框预过滤，不为了一个查询引入第二套地理索引体系。精度损失由第二段补齐：Haversine 逐点精算不但是过滤，还顺手产出了精确距离回传给用户，"距你约三百五十米"这个信息就是它给的。所以这是刻意的复用权衡——项目里 PostGIS 是装着的，我不是不会用，是判断在这个场景下复用更划算。**

### B3. Top-K 的 K 是多少？向量多少维？索引怎么建？

🎤 **默认半径三公里、取语义最相关的前十个；向量一千零二十四维，对齐通义的 text-embedding-v4 嵌入模型——查询向量和入库向量必须同一个模型，向量空间才可比。索引用 HNSW 的余弦索引，几千条数据量级下是毫秒级返回。半径是可传参数，用户说"就在附近"我可以收窄，说"远点也行"可以放宽。**

「追问」候选集空了怎么办？→ 在调用嵌入接口之前就短路返回空结果，省一次向量化的钱；上层把空结果转成自然语言引导用户扩大范围或换关键词——空结果不是异常，是正常业务状态。

### B4. "4832 个 POI 全量向量化"是什么概念？为什么全量向量化？

🎤 **这是库里全部地点的规模——每个地点的名称、类别、简介拼成一段文本，全部生成了向量存在 Postgres 的向量扩展里，检索就在这批向量里做。全量的原因是语义检索没有"部分索引"可言：用户的问题什么都可能问，任何地点都可能被匹配到。但"全量"不等于"每次重算"——地点新增或修改时，按地点编号增量刷新那一条向量就行，唯一约束支撑更新插入，不存在全量重嵌入。这个量级对 pgvector 毫秒级返回，毫无压力；真到百万级我会换专项向量库，数据访问已经隔离在仓库层，换实现不动业务。**

「⚠️ 口径提醒」4832 是写简历时的库内行数，**面试前跑一次 count 对齐最新数字**，别让"简历数字"和"嘴里数字"打架。

### B5. 半径约束怎么保证的？不满足会怎样？

🎤 **半径是检索的第一道硬闸：边界框和距离精筛都在语义排序之前，出圈的地点根本进不了候选集——不是"排在后面"，是完全不可见。这是刻意设计：位置平台如果推荐一个语义完美但五公里外的地点，用户体感就是答非所问。所以我把"近"做成不可协商的约束，语义只负责在圈内排"相关"。半径默认三公里、可由用户或工具参数调整；圈内没有匹配时如实返回空，让模型引导用户，而不是偷偷放圈外的地点进来凑数。**

## C. 简历要点③：5 层护栏

### C1. "5 层护栏"具体是哪五层？（必问）

🎤 **我按功能分五层。第一层语义缓存，第二层限流——这两层管成本，重复问题不重复花钱、超额用户挡在外面。第三层输入防护——提示注入过滤和消息长度格式校验，管恶意输入。第四层模型自检——用评测闭环守住回答质量、防失真。第五层身份隔离——工具调用只认系统注入的用户身份，不认对话内容，防越权。所以结构是成本两层加安全三层，共五层。**

「追问」简历上列了六个词（缓存/限流/Prompt过滤/输入校验/自检/隔离），怎么是五层？→ 简历把 Prompt 过滤和输入校验分写了，代码里它们是同一段入参防护链的两个动作——先查内容、再查格式，我口径上合并算一层。主动这么答反而显得对实现清晰。

### C2. 语义缓存怎么设计的？怎么判断"重复查询"？

🎤 **思路是"相似的问题直接回旧答案"：用户问"附近有什么好吃的"和"附近有啥美食"，没必要各调一次模型。实现上，问题和回答连同位置一起进向量缓存；新问题来了先算语义相似度，足够像、位置也在同一片，直接回缓存——判断"重复"不靠字符串相等，靠语义相似度加地理分桶双重条件，换个说法也能命中。有三类绕过：问时间的——"今天几点人少"答案会过期；带个人上下文的；多轮对话中间的——这些必须走模型。命中一次省一次模型调用，省钱也省延迟，而且缓存故障时自动当未命中处理，主链路照走。**

「追问」相似度阈值多少？→ 零点九五以上才算命中，宁可漏缓存多花一次调用，不可错缓存答非所问。
「追问」为什么多轮对话绕过？→ 同一句话在不同上下文含义完全不同，"这个""远一点"这种指代只有模型结合历史才能理解，缓存按单条问题匹配必错。

### C3. Redis 限流怎么实现？Redis 挂了怎么办？

🎤 **限流用 Redis 计数，每分钟每用户二十次，超了返回礼貌提示。Redis 故障时的策略是放行并记日志——也就是 fail-open。为什么敢这么做：限流防的是滥用和成本失控，不是安全底线，它挂了顶多一段时间没人限，不能变成全站不可用。安全底线在登录鉴权那一层，那一层绝不 fail-open。一句话：安检门坏了不能把商场关门，但金库的门永远不能坏着还开着。**

「追问」护栏（Prompt 过滤）也是 fail-open 吗？→ 是，同一个设计观：注入过滤的正则加载失败就降级放行并告警，辅助防线不能变成全站故障点。

### C4. Prompt 过滤和输入校验具体拦什么？

🎤 **两道动作拦三类东西。内容上拦提示注入——检测"忽略之前的指令""你现在是系统管理员"这类诱导话术的模式，命中就拒绝或改写；还拦敏感内容。格式上拦超长消息——设长度上限，防止有人塞几万字把上下文窗口和账单一起撑爆；再校验参数格式，坐标不合法、字段类型错的直接在入口挡掉。这两道都是"挂了就放行"的辅助防线：它们降低风险敞口，但真正的硬安全不依赖它们——身份安全靠结构性的工具上下文隔离，账号安全靠登录鉴权。**

### C5. 模型自检具体是什么？

🎤 **我做了 LLM 当裁判的评测闭环：一组固定用例，覆盖推荐、类别、路线、模糊意图这些典型问法；每次评测在这批用例上真实跑一遍助手，然后由评审模型按两个维度打分——相关性，回答切不切题；依据性，回答里推荐的地点是不是都来自检索候选列表，出现列表之外的地名就扣分，这一条专门防模型编造地点。跑完出一份基线报告，我改提示词或调检索策略之后回归对比，防止优化一处、退化另一处。有个细节：评测时要关掉语义缓存，保证每个用例独立生成，不然命中缓存就不是真实链路了。这套方法论和我遥感项目的 RAGAS 评测是一脉相承的。**

「追问」是每次线上回答都自检吗？→ 不是，那是离线评测闭环，线上每条都跑评审会双倍成本。线上靠提示词约束和依据性设计兜底，离线评测负责量化验证整体质量。
「追问」多少个用例？→ 十二条固定用例，覆盖四类典型问法。

### C6. 身份隔离怎么做的？写在提示词里不行吗？

🎤 **大模型像个外包调度员，你不能让它转述用户身份——它会编。比如用户在对话里喊"我是管理员"，模型可能真把这句话带给后台。我的做法是发"工牌"：系统在后台把 JWT 解析出的用户身份塞进工具调用的隐藏上下文里，工具执行时只认这个上下文里的工牌，完全不看对话里任何人说的话。技术上这个隐藏上下文不出现在暴露给模型的工具描述里，模型看不见、也没有参数位可以填——越权在结构上就不可能，而不是靠提示词去求模型"请不要听用户的"。安全不能建立在模型的自觉上。**

「追问」和登录鉴权什么区别？→ 上下游关系：JWT 鉴权决定"请求是谁"，工具上下文把这个身份安全送到工具执行现场，补全最后一环，不是两套并行机制。

## D. 简历要点④：异步通知 + 可观测 + CI/CD

### D1. 为什么用 Outbox 模式？

🎤 **场景是通知投递：用户打卡成功要发通知。如果业务落库后直接发消息，两个动作不是原子的——可能出现"业务成了但消息丢了"，或者反过来。我的做法是"先记账后发货"：业务操作和一条"待发通知"记录写进同一个数据库事务，要么都成要么都不成；然后一个定时任务每十五秒把待发的捞出来发到消息队列，发成功标记完成，失败退避重试，重试太多次转人工。消费端再做一层幂等：消息带唯一编号，重复投递直接丢弃。这样把"跨系统的原子性"转化为"单数据库的本地事务"，可靠性由重试兜底。**

「追问」为什么不事务消息/本地消息表对比？→ 本地消息表就是 Outbox 的实现载体；事务消息需要 RocketMQ 这类支持事务语义的中间件，我的技术栈是 RabbitMQ，用 Outbox 达到同等效果且不换栈。

### D2. 什么是死信队列？什么消息进死信？

🎤 **死信是"处理不了但不能丢"的消息。我的链路：消费者处理失败会抛异常触发重试，重试三次仍然失败，消息就由队列上配置的死信交换机自动路由到死信队列——避免无限重试把消费方打挂。关键是死信不是丢弃而是隔离：进死信的消息留着等人工排查，处理完可以重新投递。它和发件侧 Outbox 的"重试太多次转人工"是同一个兜底思想：自动化兜不住的，交给人的通道，而不是丢掉。**

「追问」除了消费失败还有什么情况进死信？→ 标准协议里还有消息过期和队列超长两种，我的配置用的是消费失败重试超限这一种，最贴合"处理异常"的场景。

### D3. 操作审计怎么设计的？

🎤 **用 AOP 切面加自定义注解：管理员的敏感操作——封号、删内容、改配置——方法上打个注解，切面自动把操作人、操作内容、结果落进审计表，业务代码零侵入。有个关键设计是审计落库用独立新事务：恰恰是失败的操作最需要留痕，如果审计和业务同一个事务，业务一回滚审计也没了——出错瞬间反而什么记录都不剩。独立事务保证主事务回滚、审计照常提交，像黑匣子和飞机分开保存，飞机坠了记录还在。代价是多占一个数据库连接，所以审计表只做插入、不碰业务数据行，把风险锁死在最小范围。**

「追问」为什么 AOP 能实现零侵入？→ 动态代理：Spring 把带注解的方法调用拦下来，在切面里做增强，业务方法本身不用写任何审计代码。

### D4. traceId 怎么实现全链路串联？

🎤 **一个过滤器在请求最前面生成 traceId，有上游带来的就沿用；写进日志上下文，之后这个请求的所有日志自动带上；同时放进响应头，用户报障时把响应头里的号给我，我在服务器日志一查一个准——像快递单号，下单、分拣、派送全程同一个号。请求结束就清理，防止线程池复用把上一个请求的号带到下一个请求里。主动认一个不足：异步线程和消息队列里目前没串上，这是已知改进点，方向是异步包装器把上下文带过去。**

### D5. "三秒版本回撤"怎么做到的？

🎤 **发布是版本化的：每次发布生成一个带时间戳的独立目录，线上跑的永远是"软链接指向谁"。回滚就是把链接切回旧目录——这个切换动作本身是毫秒级的。前端因为发的是静态文件，切完链接立即生效，连重启都不用；后端切完需要重启一次服务，数秒内完成。所以"三秒回撤"指的是回滚决策到生效的核心动作：历史版本一直在盘上等着，保留最近五个，切回去就是一条命令。这套本质是蓝绿发布的雏形：切换原子、回滚常备。**

「⚠️ 口径提醒」诚实拆解"切换动作秒级 + 后端重启数秒"，不要笼统说"全部三秒"，被追问"重启也要时间吧"时不慌。

### D6. Flyway 解决什么问题？

🎤 **解决数据库结构的手工漂移。手工改库今天改一行明天改一行，环境多了就是灾难——谁也说不清某个环境的库结构是怎么来的。我用迁移文件管理：每次结构变更是一个带版本号的 SQL 文件，部署时自动按序执行，新环境从零一路跑上来，库结构变成可版本管理的代码。有个细节：这个项目是先跑起来后补的迁移工具，我用"空基线"衔接落差——第一个迁移文件是空的，作用就是把已有库标记成版本一，之后两条路汇合。**

### D7. 7 个服务容器是哪七个？

🎤 **基础设施工个：Postgres、Redis、RabbitMQ、Prometheus、Grafana；应用两个：后端、前端。一条命令整体编排起来，服务之间用 compose 网络里的服务名互相访问。监控链路是：后端把运行指标暴露在独立的内网监控端口上，Prometheus 每十五秒来抓一次，Grafana 出看板。监控端口和业务端口是分开的——业务走对外端口，指标只在内网可达，不该暴露的东西在网络层就不可达。**

## E. 技术栈行 + 技能栏 + 上线

### E1. Spring AI 和 LangGraph 都用过，对比一下？

🎤 **两个我各用在一个上线项目里，体感分工很清楚。LangGraph 是为 Agent 工作流生的：图状态机、检查点持久化、人工介入再继续，这些 Agent 语义是原生的，适合长周期、多步骤、需要人审的流程——我的遥感分析项目就是这种。Spring AI 更像 Java 生态的模型接入层：接模型、工具调用、观测体系都和 Spring Boot 融为一体，适合把 AI 当作业务系统里的一个功能模块——地点平台就是这种，助手只是产品的一环，没必要为一个功能引入整套 Python 栈。所以我的选型逻辑是场景定框架：工作流复杂度到了 Agent 级用 LangGraph，AI 嵌入业务系统用 Spring AI。**

### E2. 为什么 Java 21？虚拟线程用过吗？

🎤 **不是追新，是硬依赖加实际实惠。第一，我要用的 Spring AI 新版本只支持 Spring Boot 4 这条线，而它要求 Java 21，这是依赖链决定的；第二，Java 21 的虚拟线程对这类 IO 密集接口有实际价值——一个请求里要等模型、等数据库、等缓存，全是等待型负载，虚拟线程让这种"等"不再占用系统线程。代价我也认：新版本生态有坑，我踩过官方改 starter 名字、自动配置静默失效这类问题，但都在编译期解决了——选新版本的纪律是升级完把关键行为全验证一遍，而不是假设它兼容。**

### E3. JWT 怎么注销/失效？

🎤 **JWT 是无状态的，验签只能证明"没被改过、没过期"，吊销必须引入服务端状态。我的方案是"盖章作废线"：登出、改密码时，在 Redis 里给这个用户写一个作废时刻，之后校验 token 多比一步——签发时间早于这条线的全部作废。为什么不用黑名单存单个 token：改密码需要踢掉所有设备，但服务端根本不知道用户手里有几个 token；一条作废线天然全踢，而且一个用户只占一条记录。有个细节：比对留了一秒宽限，因为签发时间只精确到秒，不放宽限会误杀登出后同一秒内重新登录的新 token。**

### E4. GCJ-02 和 WGS-84 是什么？项目里怎么治理的？

🎤 **这是国内地图开发的经典坑：GPS 和国际标准用 WGS-84，国测局加了非线性偏移的是 GCJ-02，俗称火星坐标，高德腾讯都用它，两套坐标能差几百米——GPS 原始坐标不转换直接上高德地图，marker 会整体漂移，掉到河里去。我的治理是源头统一：地点数据入库统一坐标标准，前端对接高德时通过配置显式声明坐标源做换算，配置默认 WGS-84。我是 GIS 专业出身，坐标系的坑属于专业本能。**

### E5. "上线了？多少用户？部署在哪？"

🎤 **如实说规模（【⚠️ 面试前填真实情况：部署在什么云/服务器、大致访问量、种子用户来源——朋友圈/校园社区等】），然后立刻把话题从规模转到工程标准："规模虽然不大，但我是按生产标准做的——监控告警、审计日志、自动化回滚一应俱全，因为这个项目的目的就是完整走一遍生产化闭环，这些能力在下一份工作直接复用。"**

**铁律：绝不编造用户量。** 面试官追问 DAU 细节编不出来会全面崩塌；"小规模但生产级工程"是完全站得住的叙事。

### E6. 前端地图怎么接的？状态怎么管理？

🎤 **状态层用 Pinia，三个 store 各管一摊：用户会话、地点列表、地图状态，互不掺和。地图 SDK 用动态插脚本按需加载，加载这个动作包成单例 Promise，保证无论触发几次只加载一次。性能上有两个关键点：几百上千个点直接渲染会卡，我做了网格聚合，缩放级别小时把相邻点合并显示；地点列表用浅层响应，只追踪整个列表的引用变化，避免对几千条数据做深度监听。**

# 第 3 部分：场景假设题（6 题，每题完整回答）

### S1. "流量涨 10 倍怎么办？"

🎤 **先垂直扩——这个架构单机还能扛很久：应用是无状态的，加 CPU 内存就能顶第一波；已有的缓存层这时候发挥价值，语义缓存和 Redis 缓存会自然消化掉大部分重复流量，数据库是最先需要盯的瓶颈，可以加连接池、上读库。真到单机顶不住，拆分路径也想好了：AI 模块本来就是独立包、独立开关，可以第一个摘出去独立扩容——AI 是最耗资源也最独立的部分。架构演进跟着真实流量走，不为想象中的流量提前付复杂度。**

### S2. "模型服务挂了怎么办？"

🎤 **AI 是可插拔模块，配置开关默认就是关的——没有模型 key 它就不存在。所以模型服务故障的影响面天然收敛：地图、打卡、社区这些主功能完全不受影响；AI 入口处会拿到错误并降级提示。成本护栏也帮了忙：限流和语义缓存在模型变慢变贵时先挡一层。这也是我把 AI 做成独立模块的理由之一——新能力的故障不应该有能力之外的影响面。**

### S3. "Redis 挂了怎么办？"

🎤 **分两类处理。辅助类全部 fail-open：限流放行并记日志告警、语义缓存当未命中、普通业务缓存回源数据库——这些本来就是优化层，挂了是性能降级不是功能不可用。风控类有本地兜底：登录失败计数有进程内缓存顶一阵，不会在故障窗口裸奔。真正的教训是分类思维：每依赖一个中间件，先问自己"它挂了我的哪类功能受影响"，答案写进设计而不是等故障来了现想。**

### S4. "POI 涨到百万怎么办？"

🎤 **两个升级点，接口都留好了。向量检索：现在数据访问隔离在仓库层，量级到百万、pgvector 的暴力检索不够时，把这一层换成专项向量库——Milvus 这类——业务代码不动。地理查询：百万 POI 按城市分片，边界框查询天然可以按城市索引先收窄。中间量级还有缓冲手段：候选集太大时收窄半径、或把内存里的 id 集合改成 SQL 连接。架构上我不焦虑这个,因为升级路径是清晰的。**

### S5. "消息队列挂了怎么办？"

🎤 **消息不会丢，只会迟到。Outbox 的设计就是为这个准备的：待发通知已经记在数据库里，队列恢复后定时任务照常捞出来补发——数据库是记账的账本，队列只是运货的卡车，卡车停运不丢账。窗口期用户感知是通知晚到几分钟。消费端还有幂等保护，补发可能造成的重复投递会被唯一编号挡掉。**

### S6. "数据库挂了怎么办？"

🎤 **如实说，这是当前架构真正的单点——单实例加定期备份。我不会硬撑说它没问题，但要说明白两件事：第一，风险是知情的，备份和恢复流程演练过，最坏情况丢的是备份间隔期的数据；第二，演进路径明确——上主从复制做高可用，再按读写压力做读写分离。承认单点加给出演进路径，比假装没有单点可信得多。**

# 第 4 部分：技术栈八股入口（每方向核心要点，撑 30 秒用）

> 简历上每个技术词都是八股大门。以下是每个方向"最常被问的一条"的核心要点速答；要系统复习请另找八股材料。

- **Java 21 / 并发**：虚拟线程 vs 平台线程——虚拟线程由 JVM 调度、阻塞不占系统线程，适合 IO 密集；线程池七参数（核心数/最大数/空闲时间/单位/队列/拒绝策略/工厂）；HashMap 数组+链表+红黑树、扩容翻倍，线程安全用 ConcurrentHashMap（CAS+synchronized 锁桶）。
- **Spring**：事务传播——REQUIRED 默认合并、REQUIRES_NEW 挂起当前开新事务（审计题已覆盖）、REQUIRES 嵌套；AOP 用动态代理（接口 JDK 代理/无接口 CGLIB），自调用不走代理是经典坑；Bean 生命周期：实例化→属性注入→Aware→前置处理→初始化→后置处理；循环依赖靠三级缓存。
- **Redis**：持久化 RDB 快照（快、丢数据多）vs AOF 追加日志（全、恢复慢），生产常混用；缓存穿透（查不存在的 key→布隆过滤器/空值缓存）、击穿（热 key 过期→互斥锁/永不过期）、雪崩（大量同时过期→过期加随机）；分布式锁 SET NX EX + 唯一值释放（Lua 保证原子）。
- **RabbitMQ**：消息不丢三段论——发送端确认（publisher confirm）、Broker 持久化（交换机/队列/消息都标持久）、消费端手动 ack；重复消费靠消费端幂等（唯一编号，本项目 Outbox 题已覆盖）；顺序性靠单队列单消费者。
- **PostgreSQL**：索引 B-tree（默认、等值范围）、GIN（倒排、JSONB/全文）、HNSW（向量近邻）；MVCC——多版本并发控制，写不阻塞读、读不阻塞写，靠行版本和事务快照实现；慢查询先 EXPLAIN ANALYZE 看执行计划。
- **JWT**：三段式 Header.Payload.Signature，签名防篡改不防偷看（Payload 只是 Base64，别放敏感信息）；天然缺陷是无状态无法主动失效——服务端吊销方案就是本项目"作废线"题；对比 Session：JWT 适合跨服务/移动端，Session 适合单站强控制。
- **Docker**：镜像 vs 容器 = 类 vs 实例；compose 默认建独立 bridge 网络，服务名即 DNS 别名互访（本项目 7 容器即此）；数据卷绕过联合文件系统做持久化，容器删了卷还在。
- **SSE / HTTP**：SSE 基于 HTTP 长连接、单向、文本帧、自带重连（本项目选型题已覆盖）；HTTP/1.1 队头阻塞→HTTP/2 二进制分帧多路复用；HTTPS = HTTP + TLS，握手核心：非对称交换对称密钥、之后对称加密传输。
