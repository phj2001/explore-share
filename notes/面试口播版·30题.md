# 🎤 面试口播版 · 30 题（好背版）

> 与《面试紧急备战·标准答案库.md》配对使用。**背诵以本文档为准，追问下钻用答案库。**

## 使用方法：两层弹药

- **第一层（背这个）**：每题一段 150-220 字口播稿，40-60 秒说完。零类名、零行号、每题最多 2 个数字。
- **第二层（被追问再翻）**：面试官问"具体怎么实现 / 参数是多少"时，按每题末尾的下钻指针翻《标准答案库》对应节。

**铁律**：口播里不出现 key 名、包名、行号；专有名词只允许栈级别（Postgres/Redis/RabbitMQ）；数字每题 ≤2 个，多一个都别背。

## 万能骨架（30 题共用一个节奏，背 5 题后其余自动展开）

1. **开口定调**（10 秒）：一句话说清这是什么 / 我选了什么
2. **问题**（10-15 秒）：不用它会怎样 / 需求从哪来
3. **做法**（25-30 秒）：≤3 步，动词开头，白话表达
4. **为什么 / 效果**（10-15 秒）：选它的理由 + 一句 trade-off

## 一、🔴 P0 十题（必背，时间只够就背这些）

### 1. 为什么单体而不是微服务（原 #2）

> 这个项目从第一天就是我一个人全栈开发，用户量是校园到城市级别，所以我选了单体。微服务的价值是多人团队并行开发和独立伸缩，但我一个人维护，拆微服务只会带来分布式事务、跨服务排障、部署复杂度翻倍这些成本，收益接近零。做法上是一个 Spring Boot 应用按模块分包，比如 AI 助手整体一个包、默认可关；Postgres、Redis、消息队列这些中间件用 Docker Compose 一键起；生产就是单机一个进程加 systemd 管理。模块边界靠包结构约束，真要拆的时候 AI 模块可以整体摘出去——架构要匹配团队规模，而不是匹配简历。

**必背数字**：1 个应用进程。
**比喻钩子**：一个人的小店不需要拆成七个部门。
**被追问 →** 标准答案库 #2（compose 细节、与 AI 模块解耦）。

### 2. 一次 AI 对话请求的完整生命周期（原 #3）

> 我按五步讲：安检、查缓存、组装上下文、调模型、流式返回。请求先过两道闸——限流和内容护栏：限流是每分钟每用户二十次，护栏拦提示注入和超长消息，这两个都设计成"挂了就放行并记日志"，因为它们是辅助防线，不能变成全站故障点。然后查语义缓存：如果用户问题和地理位置都和历史问题高度相似，直接回缓存的答案，省一次模型调用。没命中就组装上下文：系统提示词、最近几轮对话、检索出来的附近地点、再加上用户身份。最后调大模型，流式逐字回传前端。这条链路每一层都可以独立开关，坏了不互相拖累。

**必背数字**：20 次/分。
**比喻钩子**：安检 → 查旧账 → 备料 → 上菜。
**被追问 →** 标准答案库 #3（SSE 超时、护栏正则清单、伪流式成因）。

### 3. 空间约束 RAG 三段式 ⭐核心亮点（原 #5）

> 用户问"附近适合带娃的地方"，我分三步：先画方框、再量距离、最后比语义。第一步以用户位置为圆心按半径画一个外接方框，数据库先把框外的全部排除——方框查询便宜，走普通索引就行。第二步框的四角其实超出半径，用球面距离公式精确算一遍，把真圆外面的剔掉。第三步剩下的少量候选才做向量语义排序，取最相关的几个。核心思想是"先便宜后昂贵"：语义计算是最贵的一步，我把它压到最后、只对几十个候选做，而不是对全库做。这也是我这套和通用 RAG 最大的区别——先问你在哪，再谈像不像。

**必背数字**：三步顺序（方框 → 圆 → 语义）。
**比喻钩子**：找餐厅先看哪个街区，再看具体多远，最后挑口味。
**被追问 →** 标准答案库 #5（radius 默认值、Haversine、为什么不用数据库空间函数）。

### 4. 你的 RAG 和通用 RAG 有什么不同（原 #6）

> 通用 RAG 是全库找语义最像的，我的是"先问你在哪，再谈像不像"，三个差异。第一，检索前有地理围栏：出圈的地点语义再像也不进候选，位置平台的答案必须贴着用户。第二，不单独建向量库，用 Postgres 的向量插件，业务数据和向量在同一个库里，一个事务、一套备份，省掉一个有状态服务的运维。第三，缓存也带位置：同一个问题在不同城市答案不同，所以缓存比对时把经纬度也揉进去。效果是检索天然贴业务，成本和运维都可控。

**必背数字**：三个差异。
**比喻钩子**：向量库只是"锦上添花层"，不值得为它单开一家店。
**被追问 →** 标准答案库 #6（pgvector 选型权衡、量级到了怎么办）。

### 5. ToolContext 怎么防 LLM 越权 ⭐⭐（原 #8）

> 大模型像个外包调度员，你不能让它转述用户身份——它会编。比如用户在对话里喊"我是管理员"，模型可能真把这句话带给后台。我的做法是发"工牌"：系统在后台把用户身份塞进工具调用的隐藏上下文里，工具执行时只认这个上下文里的工牌，完全不看对话里任何人说的话。代码上就是工具方法多一个上下文参数，从里面取用户 ID 去查数据。这样越权在结构上就不可能，而不是靠提示词去求模型"请不要听用户的"——安全不能建立在模型的自觉上。

**必背数字**：1 个上下文参数。
**比喻钩子**：工具只刷工牌，不听口头报身份。
**被追问 →** 标准答案库 #8（5 个工具清单、为什么不放提示词）。

### 6. 为什么伪流式而不是真流式 ⭐⭐（原 #9）

> 我本来做的是真流式，上线发现模型网关的流式接口有 bug，会随机断流，这是官方 issue 里确认的问题。我改成"伪流式"：后端一次性拿到完整回答，然后切片定时往前端推，用户的观感和打字机完全一样。这里的关键是想清楚用户要什么——用户要的是"答案逐字出现"的感知，中间是不是真空流没人看得见。同时我留了升级开关，官方修好后一行配置切回真流式。这个事给我的经验是：遇到基础设施 bug，先用最小改动保住用户体验，同时给修复路径留门。

**必背数字**：无（故意零数字，讲故事就行）。
**比喻钩子**：后厨一次炒完，服务员分段上菜。
**被追问 →** 标准答案库 #9（官方 issue 编号、分块大小、切换开关）。

### 7. 为什么用 Outbox 模式（原 #14）

> 场景是通知投递：用户打卡成功要发通知。如果业务落库后直接发消息，两个动作不是原子的——可能出现"业务成了但消息丢了"，或者反过来。我的做法是"先记账后发货"：业务操作和一条"待发通知"记录写进同一个数据库事务，要么都成要么都不成；然后一个定时任务每十五秒把待发的捞出来发到消息队列，发成功标记完成，失败退避重试，重试太多次转人工。消费端再做一层幂等：消息带唯一编号，重复投递直接丢弃。这样从"跨系统的原子性"转化为"单数据库的本地事务"，可靠性由重试兜底。

**必背数字**：15 秒调度。
**比喻钩子**：先记账后发货，账本和生意在同一笔账里。
**被追问 →** 标准答案库 #14（三态状态机、退避时间、死信处理）。

### 8. 批量调度为什么故意不加 @Transactional ⭐⭐（原 #15）

> 这里有个 Spring 的经典坑：定时任务方法里调自己类的方法，走的是 this 引用、不经过代理，事务注解等于白贴。但我的答案不是绕过代理，而是压根不需要整批事务。批量投递的正确语义是：每条记录发完消息就单独保存一次状态，一条失败不影响其他条。如果加整批事务，一条卡住整批回滚，重试还全部重来，而且长时间占着数据库连接。所以正解是让每条记录自己管自己——单元越小，事务越不需要。

**必背数字**：无。
**比喻钩子**：一卡车货一件件签收，不要整车一起签。
**被追问 →** 标准答案库 #15（AOP 代理原理、自调用细节）。

### 9. 这个项目最大的短板（原 #28）

> 最大短板是测试覆盖，我如实说：单测有十几个类，但核心链路的集成测试没有，前端测试是零。为什么还敢上线：CI 每次部署都会跑单测，所以已有的是"拦门的"；缺的是核心链路的回归保护。我的补救方案也很明确：用 Testcontainers，让数据库和扩展用真容器起、不起 mock，两三天能把最核心的三五条链路补上。测试欠的债我心里有数、有优先级、有路线——这比遮掩强。

**必背数字**：十几个单测类。
**比喻钩子**：主动认 + 代价知情 + 补救路线，三步走。
**被追问 →** 标准答案库 #28（其他短板一句话带过、伪流式短板答法）。

### 10. 这项目主要 AI 写的吧？你真的懂吗 ⭐核心压力题（原 #29）

> 坦白讲 AI 参与度确实很高，但我对"懂"的标准是：能不能为每个技术决策负责。第一，每个关键设计我都能讲 trade-off，比如 JWT 吊销为什么用时间戳作废线而不是 token 黑名单——存储和"改密踢全部设备"两个维度我都比过。第二，我踩的坑是一手的：升级 Spring Boot 4 时官方改了包名导致配置静默失效，这种坑抄不来，只有真跑过才知道。第三，代码里"为什么这么做"的注释是我复核过的。AI 时代用 AI 开发是基本功，我的价值在架构判断和验收——AI 给十个方案，选哪个、怎么验证是我的活。

**必背数字**：无。
**比喻钩子**：不辩解，直接展示"我懂"的三个证据。
**被追问 →** 标准答案库 #29（现场写代码应对、具体坑细节）。

## 二、🟠 P1 十题（高频追问与亮点深挖）

### 11. 为什么 AI 助手默认关闭、做成独立模块（原 #4）

> AI 功能我做成"可插拔"的：配置开关默认关，没有模型 API key 它就不存在。三个理由：成本上，模型调用花真金白银，默认开等于给每个环境埋一张账单；稳定性上，AI 服务挂了不能影响地图、打卡这些主功能；工程上，AI 整体一个包、对外只暴露一个接口，想摘随时能摘。效果是演示时配个 key 就亮，平时零成本零风险。

**必背数字**：1 个开关。
**比喻钩子**：可选配件不焊死在主板上。
**被追问 →** 标准答案库 #4。

### 12. 语义缓存怎么设计的，哪些情况绕过（原 #7）

> 思路是"相似的问题直接回旧答案"：用户问"附近有什么好吃的"和"附近有啥美食"，没必要各调一次模型。实现上，问题和回答连同位置一起进向量缓存；新问题来了先算相似度，足够像、位置也在同一片，直接回缓存。三类绕过：问时间的（"今天几点人少"答案会过期）、带个人上下文的、多轮对话中间的——这些必须走模型。命中一次省一次调用，省钱也省延迟。

**必背数字**：三类绕过。
**比喻钩子**：问路的人换了说法，指的还是同一条路。
**被追问 →** 标准答案库 #7（相似度阈值、位置分桶、过期清理）。

### 13. 限流 + 护栏为什么都 fail-open（原 #12）

> 这两个都是辅助防线，设计原则统一：它们挂了不能拖垮主功能。限流用 Redis 计数，每分钟每用户二十次，超了返回礼貌提示；Redis 故障时就放行并记日志。护栏是几类提示注入的正则加消息长度上限，规则加载失败同样降级放行。为什么敢这么做：它们防的是滥用和成本失控，不是安全底线——安全底线在登录鉴权那一层，那层绝不 fail-open。安检门坏了不能把商场关门，但金库的门永远不能坏着还开着。

**必背数字**：20 次/分。
**比喻钩子**：安检门 vs 金库门。
**被追问 →** 标准答案库 #12（正则清单、key 设计、计数过期）。

### 14. 多轮对话记忆怎么存（原 #13）

> Redis 里按会话 ID 存一个列表，一问一答两条消息，只保留最近六轮、半小时不用就过期。为什么这么轻：上下文窗口有限，历史塞太多又贵又稀释重点，六轮足够接住"再推荐几个"这类指代；会话本身是短生命周期的，不值得落库沉淀。过期自动删，连清理任务都不用。

**必背数字**：6 轮 / 30 分钟。
**比喻钩子**：聊天记忆像白板，写满了擦最旧的。
**被追问 →** 标准答案库 #13（裁剪策略、和语义缓存的关系）。

### 15. JWT 怎么吊销（原 #17）

> JWT 是无状态的，验签只能证明"没被改过、没过期"，吊销必须引入服务端状态。我的方案是"盖章作废线"：登出、改密码、找回密码时，在 Redis 里给这个用户写一个作废时刻，之后校验 token 就多比一步——签发时间早于这条线的全部作废。为什么不用黑名单存单个 token：改密码需要踢掉所有设备，但服务端根本不知道用户手里有几个 token；一条作废线天然全踢，而且一个用户只占一条记录。有个细节：比对时留了一秒宽限，因为 token 的签发时间只精确到秒，不放宽限会误杀登出后同一秒内重新登录的新 token。

**必背数字**：1 秒宽限。
**比喻钩子**：盖章作废线——这条线之前发的票全作废。
**被追问 →** 标准答案库 #17（为什么时间戳方案、TTL 设计）。

### 16. 登录风控怎么设计（原 #18）

> 两层保险。第一层 Redis 计数：同一账号密码连错五次，锁十五分钟，锁的是账号不是 IP，换网也绕不过。第二层本地内存兜底：Redis 万一挂了，用进程内缓存顶一阵，不让风控在故障时裸奔。还有个细节：用户名不存在的尝试也计失败——不然有人可以拿登录接口探测哪些用户名注册过。风控的核心诉求是"宁可错杀不可放行暴力破解"，同时正常用户输错几次也不至于被永久锁。

**必背数字**：5 次 / 锁 15 分钟。
**比喻钩子**：双保险——电子锁坏了还有机械锁。
**被追问 →** 标准答案库 #18（锁粒度、本地缓存清理）。

### 17. 用户信息缓存角色变更为什么要主动清（原 #19）

> 每个请求鉴权时都要查用户状态和角色，不能次次打数据库，所以 Redis 缓存五分钟。问题在这：管理员封禁一个用户后，缓存里还是"正常"，这个被封的人最多还能蹦跶五分钟——对治理场景这就不够了。所以所有改状态的地方，封禁、改角色、改密码、登出，都主动删缓存，下一个请求回源拿最新的。这是缓存一致性的经典处理：写路径主动失效，过期时间只是兜底，两者缺一不可。

**必背数字**：5 分钟。
**比喻钩子**：门禁卡挂失了要立即生效，不能等月底同步。
**被追问 →** 标准答案库 #19（清缓存的所有触发点清单）。

### 18. actuator 端口怎么收窄（原 #22）

> 监控端点里有健康检查、运行指标这类内部信息，我把它们从主端口剥出去：业务走 8080 对公网，监控单独一个 9091 端口，只在内网和容器网络里可达，Prometheus 从内网来抓取。这是网络层隔离，比在应用层校验路径硬得多——不该可达就物理不可达。这里我踩过一个升级的坑：框架大版本升级时官方改了一批配置类的包名，我的排除项静默失效，不报错但行为变了，最后是编译期暴露出来的。所以新框架升级要专门盯这类"沉默的变更"。

**必背数字**：8080 / 9091。
**比喻钩子**：员工通道和顾客大门分开开。
**被追问 →** 标准答案库 #22（EPP 注册机制、踩坑细节）。

### 19. UGC 治理怎么闭环（原 #27）

> 两层闭环。事前是脱敏：用户发内容时过一遍敏感词过滤，命中的词自动打码，不拦截发布——命中率低，命中就拒发会误伤正常用户，打码既保证入库合规又不伤体验。事后是举报：其他用户举报后进待处理队列，管理员核实可以删内容、封账号，举报时还会把内容存快照，防止删了之后没法对证。词库本身挂了怎么办？降级不过滤并告警——它是辅助层，不能变成全站发不了内容的单点。这和 AI 限流的 fail-open 是同一个设计观。

**必背数字**：两层闭环。
**比喻钩子**：先过安检门，漏了的靠监控抓。
**被追问 →** 标准答案库 #27（DFA 原理、接入点清单、举报去重）。

### 20. GitHub Actions 部署链路（原 #24）

> 推主干分支自动触发：云端先把后端打成 jar、前端构建成静态文件，然后通过 SSH 传到服务器，执行两个部署脚本完成上线，全程无人工。脚本做三件事：新版本放进带时间戳的目录、把软链接切到新目录、重启服务；历史版本保留最近五个。为什么不上 Kubernetes 这类重的：单机规模一分钟内发布完，回滚就是把链接切回去，朴素但可靠，复杂度要匹配规模。

**必背数字**：保留 5 个版本。
**比喻钩子**：流水线一键到岗，机器人搬货机器人摆。
**被追问 →** 标准答案库 #24（workflow 步骤细节、密钥管理）。

## 三、⚪ P2 十题（覆盖面，防冷门）

### 21. 为什么 Spring Boot 4 + Java 21（原 #1）

> 不是追新，是两个实际理由。第一，我要用的 Spring AI 新版本只支持 Boot 4 这条线，而 Boot 4 要求 Java 21，这是硬依赖链；第二，Java 21 的虚拟线程对这类 IO 密集接口有实际实惠。代价我也认：新版本生态有坑，我踩过官方改 starter 名字、自动配置静默失效这类问题，但都在编译期解决了——选新版本的纪律是升级完把关键行为全验证一遍，而不是假设它兼容。

**必背数字**：无。
**比喻钩子**：想要新发动机，就得换配套的车架。
**被追问 →** 标准答案库 #1（BOM 版本链、starter 改名清单）。

### 22. 为什么 PostGIS + pgvector 不用专门向量库（原 #10）

> 我的场景里向量只是最后一层锦上添花，数据量级几千上万条，专门向量库的杀手锏——亿级数据、分布式索引——完全用不上；但它带来的成本是实打实的：多一个有状态服务，部署、备份、监控、升级全都单独管一套。复用 Postgres 的话，业务数据和向量同一个库同一个事务，备份恢复一套搞定。真到量级上亿再换也来得及，数据访问已经隔离在一个仓库类里，换实现不动业务。

**必背数字**：无。
**比喻钩子**：家里放个书架就够，不用租仓库。
**被追问 →** 标准答案库 #10（HNSW 索引、维度参数）。

### 23. 向量表为什么用 JdbcTemplate 不用 JPA（原 #11）

> 因为向量查询的 SQL 本身就是 JPA 方言不认识的：向量字面量、相似度操作符、冲突时更新的写法，这些只能手写原生 SQL。而 JPA 的价值在对象映射，这张表就三个字段、查询就一条，对象映射没什么可映射的——手写反而干净、可控、看得见真实 SQL。这类选择的判断标准就是：ORM 用在它省事的地方，别扭的地方直接写 SQL，不硬凑。

**必背数字**：3 个字段。
**比喻钩子**：筷子夹牛排，不如直接用刀叉。
**被追问 →** 标准答案库 #11（SQL 原文、相似度表达式）。

### 24. Flyway 空 baseline 是怎么回事（原 #20）

> 这个项目是先跑起来后来才补的迁移工具，中间有个落差：数据库已经存在，但没有任何迁移记录。我用"空基线"填这个落差：第一个迁移文件是空的，作用就是把现有库标记成版本一，之后的变更全部走迁移文件，新环境则从建库脚本一路跑上来，两条路最终汇合。为什么坚持上 Flyway：手工改库一定会漂移，今天改一行明天改一行，部署多了就是灾难；迁移文件让库结构变成可版本管理的代码。

**必背数字**：版本 1 = 空文件。
**比喻钩子**：从今天开始记账，昨天的账封个存档。
**被追问 →** 标准答案库 #20（双轨制细节、为什么不可逆）。

### 25. traceId 怎么全链路串联（原 #21）

> 一个过滤器在请求最前面生成 traceId，有上游带来的就沿用；写进日志上下文，之后这个请求的所有日志自动带上；同时放进响应头，用户报障时把响应头里的号给我，我在服务器日志一查一个准。请求结束就清理，防止线程池复用把上一个请求的号带到下一个请求里。主动认一个不足：异步线程和消息队列里目前没串上，这是已知的改进点，方向是异步包装器把上下文带过去。

**必背数字**：无。
**比喻钩子**：快递单号——下单、分拣、派送全程同一个号。
**被追问 →** 标准答案库 #21（三落点、优先级、Micrometer Tracing）。

### 26. 审计落库为什么用 REQUIRES_NEW（原 #23）

> 场景是操作审计：恰恰是失败的操作最需要留痕。如果审计和业务在同一个事务里，业务回滚会把审计一起带走——出错瞬间恰恰什么记录都没了。所以审计落库开独立新事务：主事务回滚，审计照常提交，成功失败都有账。代价是多占一个数据库连接、且要小心自锁，所以审计表只做插入、不碰业务数据行，把风险锁死在最小范围。原则就一句：失败单元决定事务边界——业务和它的日志不能死在同一个事务里。

**必背数字**：无。
**比喻钩子**：黑匣子和飞机分开保存——飞机坠了记录还在。
**被追问 →** 标准答案库 #23（双入口设计、UnexpectedRollbackException）。

### 27. 版本化发布 + 软链接 + 回滚（原 #25）

> 每次发布生成一个带时间戳的独立目录，线上跑的永远是"软链接指向谁"。发布就是把新目录放好、链接切过去；回滚就是把链接切回旧目录——后端切完重启一次，前端因为发的是静态文件，切完链接立即生效，连重启都不用。历史版本保留最近五个，磁盘可控。这套本质上是蓝绿发布的雏形：切换是原子操作，旧版本随时还在盘上等着。

**必背数字**：保留 5 个。
**比喻钩子**：舞台换布景——新景片先搭好，灯一关一开就换。
**被追问 →** 标准答案库 #25（脚本细节、迁移不可逆的应对）。

### 28. Pinia + 高德地图怎么集成（原 #26）

> 状态层三个 store 各管一摊：用户会话、地点列表、地图状态，互不掺和。地图 SDK 用动态插脚本按需加载，加载这个动作包成单例 Promise，保证无论触发几次只加载一次。性能上有两个关键点：几百上千个点直接渲染会卡，我做了网格聚合，缩放小时把相邻点合并显示；地点列表用浅层响应，只追踪整个列表的引用变化，避免对几千条数据做深度监听。

**必背数字**：3 个 store。
**比喻钩子**：地图懒加载像点外卖，要看的时候再下单。
**被追问 →** 标准答案库 #26（聚合算法、key 安全认知）。

### 29. 面试官问"你有什么问我"（原 #30）

> 我准备三类问题，都往"我已经在想怎么做好这份工作"上靠。第一，团队现在怎么用 AI 工具开发、有没有沉淀规范——我自己的工作流是 AI 深度参与的，想对齐。第二，这个岗位前三个月最要紧的一件事是什么——把预期摆到桌面上。第三，团队的技术决策一般怎么形成、技术债怎么排优先级。避开薪资假期这类该问 HR 的，也避开官网上查得到的——反问环节是展示思维方式的最后机会，不是福利咨询。

**必背数字**：三类问题。
**比喻钩子**：问"我怎么干活"，不问"你给多少"。
**被追问 →** 标准答案库 #30（不同规模公司的问法差异）。

### 30. 追问兜底：遇到完全没背过的问题怎么办

> 三步兜底。第一步，从已知推未知：把问题往背过的骨架上靠——"这个问题本质是缓存一致性/事务边界/失败隔离"，骨架通用。第二步，坦诚 + 推理：没做过的直说没做过，但给出"如果要做我会怎么想"——面试官要的是推理过程不是标准答案。第三步，控制粒度：答到"方案选型 + 理由"就停，别硬编细节往深处说，细节说不圆会反噬。万一下钻到记不清的数字，就说"具体数值我记得大概量级，准确数字我可以查"，比编一个精确的错误数字强得多。

**必背数字**：三步。
**比喻钩子**：不会的题用骨架接，别硬背台词。
