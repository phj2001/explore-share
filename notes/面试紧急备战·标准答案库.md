## R1 · 架构与开场

### 1. 为什么 Spring Boot 4 + Java 21，而不是 SB3 + Java 17？踩过坑吗？（原 Q1 · ⚪）
**考察**：技术跟进的动机 + 新版本风险认知

#### 标准参考答案（基于代码）
选型因果链（`pom.xml` 有原话注释）：**要用 Spring AI 2.0 → 必须Boot 4 → 顺带 Java 21**。
- 项目核心卖点是 AI 助手（RAG/Agent），需要 Spring AI 2.0 的 ChatClient 编排、ToolContext、向量能力；
- `pom.xml` 注释：**"Spring AI 2.0 BOM：唯一兼容 Spring Boot 4 的线（构建于 Boot 4 + Framework 7，要求 Java 21）；1.x 仅支持 Boot 3.x，不可用"**；
- 所以不是"追新"，是被 AI 生态绑定的必然结果。

真实踩坑清单（都有代码证据）：
1. **starter 改名**：`spring-boot-starter-aop` → `spring-boot-starter-aspectj`；`spring-boot-starter-web` → `spring-boot-starter-webmvc`（pom 里就是新名字）；
2. **EnvironmentPostProcessor 包迁移**：`org.springframework.boot.env` → `org.springframework.boot`（见 `AssistantAutoConfigureExclusionEnvironmentPostProcessor`，注释明确记录），且 `spring.factories` 注册 key 必须用新 FQN，否则**静默不生效**；
3. **JSpecify 注解**：Framework 7 空安全注解换成 `org.jspecify.annotations.NonNull`（`RequestTraceFilter` 的 import）；
4. MeterRegistryCustomizer 包迁移（actuate → micrometer.metrics.autoconfigure，详见 Q32）。

#### 预埋追问逐条拆解
① **Framework 7 对我的实际影响**：就是上面四条——starter 改名、两处包迁移、JSpecify。都属于"编译期能发现或静默失效"的坑，靠 Migration Guide 逐条排掉。
② **EnvironmentPostProcessor 踩过吗**：踩过。这个类用来在 AI 助手关闭时动态排除 Spring AI 的 6 个 OpenAi*AutoConfiguration（api-key 可空、无需占位串 hack）。迁移时 import 和 spring.factories 的 key 要同时换新 FQN，只改一处就是静默失效。
③ **生态文档少怎么办**：三级手段——官方 Spring Boot 4.0 Migration Guide（代码注释里就引用了）；直接读自动配置类源码；GitHub issue 求证（AI 伪流式的根因就是查到 spring-ai#4790 / spring-ai-alibaba#1025 并验证仍未修复）。
④ **重选会怎样**：带 AI 的项目仍选 SB4——Spring AI 2.0 绑定 Boot 4，这是硬约束；若是纯 CRUD 无 AI 项目，会选 SB3 稳妥线，不必为新而新。

#### 🎤 面试版总结（可直接背）
"选 SB4+Java21 不是追新，是被 Spring AI 绑定的：项目核心是 AI 助手，Spring AI 2.0 是唯一兼容 Boot 4 的版本线，1.x 只支持 Boot 3，而这条线要求 Java 21，整条技术栈就定了。Boot 4 基于 Framework 7，我踩的坑都有记录：starter 改名，aop 变 aspectj、web 变 webmvc；EnvironmentPostProcessor 从 boot.env 包移到 boot 包，spring.factories 的注册 key 不跟着换就静默失效。文档少就靠官方 Migration Guide、读自动配置源码、查 GitHub issue——比如 AI 流式加工具调用的兼容缺陷，就是我在 spring-ai 的 issue 里确认的。重选的话，带 AI 我还是选 SB4，纯 CRUD 项目我会用 SB3，不为新而新。"

#### ⚠️ 卡壳点
因果别说反：不是"想用 Java 21 所以上 Boot 4"，而是"要用 Spring AI 2.0 → 必须 Boot 4 → 顺带 Java 21"。

### 2. 为什么单体而不是微服务？（原 Q2 · 🔴P0）
**考察**：架构选型权衡（是否理解微服务解决的问题边界）

#### 标准参考答案（基于代码）
判断依据：微服务解决的是**组织规模、独立伸缩、故障隔离**三类问题，本项目（单人开发、约 5000 行 Java、校园/社区级用户量）一个都不存在；引入只会带来服务发现、跨服务事务、分布式链路追踪的复杂度净增。

但我做的是**模块化单体（modular monolith）**，不是大泥球，证据在代码里：
- **AI 模块整体可拔**：`assistant` 包所有 Bean 挂 `@ConditionalOnProperty(app.assistant.enabled)`，默认 false 时控制器/服务/限流/护栏全部不装配；再由 EnvironmentPostProcessor 动态排除 Spring AI 自动配置 → AI 挂了/欠费，主功能零影响（README 工程化亮点原文："助手关闭时……api-key 可空"）；
- **MQ 可降级**：`RABBITMQ_ENABLED=false` 时通知走同步发送，无 RabbitMQ 也能跑；
- **存储抽象**：`StorageService` 接口 + LocalFileStorage 实现，未来切 OSS/MinIO 无感；
- **部署形态印证**：Docker Compose 7 个容器里只有 1 个后端应用容器（其余是 Postgres/Redis/RabbitMQ/Prometheus/Grafana/前端），生产就是一个 systemd 服务 `place-explore-backend.service`。

#### 预埋追问逐条拆解
① **单体瓶颈在哪**：垂直扩展上限（无法按模块独立扩容）；单进程故障域（一处内存泄漏拖垮全部）；LLM 阻塞调用虽已隔离到 boundedElastic，仍共享进程资源。但当前量级这些都不是真实瓶颈。
② **什么规模会拆**：先看团队再看流量——多人并行开发在同一模块频繁冲突、或 AI 推理负载与 CRUD 差异大到需要独立伸缩时。团队规模通常比 QPS 更早触发。
③ **先拆哪个**：AI 助手模块。三个理由：边界最干净（assistant 包自包含，对外只依赖 ChatClient/工具接口）；已有开关和独立配置，天然预留了进程边界；负载特征差异最大（LLM 秒级~十秒级 vs CRUD 毫秒级）。
④ **前后端分离算微服务吗**：不算。那只是"静态资源 + API"的部署形态分离，没有服务治理、独立数据所有权、进程间通信契约这一套。我说的单体指后端单进程。

#### 🎤 面试版总结（可直接背）
"这是有意识的权衡。微服务解决的是多团队协作、独立伸缩、故障隔离，我这个单人开发、五千行、校园级用户量的项目一个都不占，引入只会平添服务发现、分布式事务、全链路追踪的复杂度。但我做的是模块化单体：AI 助手整个包用 @ConditionalOnProperty 开关控制，默认关闭时连 Spring AI 的自动配置都被 EnvironmentPostProcessor 动态排除，AI 挂了主功能零影响；通知有 MQ 开关可同步降级；文件存储收口成 StorageService 抽象随时切 OSS。真到要拆的那天，第一个拆 AI 模块——它边界最干净、负载和 CRUD 差两个量级。前后端分离只是部署形态，不算微服务。"

#### ⚠️ 卡壳点
必须主动说出"模块化单体 + 开关"这套主动设计，否则必被追问"你就是不会微服务吧"；拆分顺序答"AI 模块"并给出边界/负载两条理由。

### 3. 一分钟讲一次 AI 对话请求的完整生命周期（原 Q5 · 🔴P0）
**考察**：整体链路熟练度（自我介绍后的必考题）

#### 标准参考答案（基于代码，逐步核对过）
前提：`app.assistant.enabled=true`，否则 `AssistantController` 根本不装配（404）。

1. **RequestTraceFilter**（@Component 注册的 servlet 过滤器，Security 链之后、DispatcherServlet 之前）：解析/生成 traceId → 写 MDC + 响应头 `X-Trace-Id`；
2. **JwtAuthenticationFilter**（addFilterBefore 于 UsernamePasswordAuthenticationFilter）：提取 Bearer → 验签取 userId → 查 Redis `jwt:revoke_before:{userId}` 黑名单（iat < revoke_before − 1000ms 视为吊销）→ 查 `user:info:{userId}` 缓存（`status:role` 格式，5 分钟 TTL，未命中回源 DB）→ DISABLED 直接 401 → 注入认证（principal=userId，权限=role）；
3. **SecurityConfig**：`/api/assistant/**` 要求 authenticated；
4. **AssistantController.chat（请求线程内、开流之前完成全部拒绝判断）**：
   - `rateLimiter.allow(userId)`：Redis INCR `assistant:rl:{userId}:{epochMinute}` 固定窗口，首次置 70s 过期，超限抛 `BusinessException(429)`；Redis 故障 **fail-open** 放行；
   - `guard.check(message)`：非空 → strip → 长度上限（默认 500）→ 7 条提示词注入正则（"忽略以上指令/ignore previous/system prompt/越狱"等），违规 400；
   - `new SseEmitter(120_000L)`（2 分钟超时），订阅 chatService.stream；onTimeout/onError/onCompletion 均 `dispose()`——防止客户端断开后 boundedElastic 上的 LLM 调用继续白烧 token；
5. **AssistantChatService.stream（boundedElastic 线程）**：
   - 计数 `assistant.chat.requests` + 计时；
   - `loadHistory(conversationId)`（Redis List 会话记忆）；
   - `cacheable = history.isEmpty() && 非时效性问题`（时间/天气/新闻等关键词正则绕过；多轮一律绕过——"这个""远一点"脱离上下文缓存必答非所问）；
   - 语义缓存命中：补写双向记忆 + 按 **30 字/块** 直接回放（cache=hit）；
   - 未命中：`chatClient.prompt().system(11 条规则的系统提示词).messages(history).user(注入当前时间+经纬度+建议半径+消息).tools(explorerTools).toolContext(userId).call().content()`——**非流式 call()**（官方 workaround，绕 spring-ai#4790 流式+工具缺陷），`subscribeOn(boundedElastic)` 不占请求线程；
   - 期间 LLM 自主调工具：recommendNearbyPlaces / searchPlaces / planRoute / listCategories / getUserPreferences，检索内部是三段式 **bbox 粗筛 → Haversine 精算 → pgvector 语义 Top-K**；**userId 只走 ToolContext**，模型不可见不可篡改；
   - 完成：写语义缓存 + 写双向记忆 + 记 latency → 回复按 30 字/块 Flux 回放，前端 SSE 逐块收到；指标（requests / cache hit-miss-bypass / latency）进 Prometheus。

#### 预埋追问逐条拆解
① **经过哪些过滤器/切面**：RequestTraceFilter（servlet 层）→ Spring Security 链（JwtAuthenticationFilter）→ DispatcherServlet → Controller → reactive 订阅。AI 对话**不在** AOP 审计范围（操作审计面向后台写操作，REQUIRES_NEW）——别顺嘴说"每步都有审计切面"。
② **哪步最耗时**：LLM `call()` 端到端（含多轮工具往返），秒级到十秒级；所以同步拒绝判断全在请求线程先做完，重活整体挪到 boundedElastic。
③ **限流命中返回什么**：在开 SseEmitter **之前**抛 `BusinessException(429, "请求过于频繁")`，走全局异常处理返回 JSON——不会出现"流已打开才报错"的尴尬状态。
④ **traceId 怎么串全程**：RequestTraceFilter 生成 → MDC（日志 pattern 自动带）→ 响应头 X-Trace-Id 给前端 → finally 里 remove，防止线程池复用串号。

#### 🎤 面试版总结（可直接背，约 60 秒）
"以 POST /api/assistant/chat 为例。请求先过 RequestTraceFilter 生成 traceId 写入 MDC；再过 JWT 过滤器：验签、查 Redis 的 revoke_before 吊销黑名单、查 user:info 五分钟缓存确认账号未禁用，注入认证；Security 层要求 assistant 路径登录。进 Controller 后，开流之前先做两道同步拒绝：每用户每分钟的 Redis 固定窗口限流，超限直接 429；护栏检查长度和提示词注入特征，违规 400。然后开一个两分钟的 SseEmitter。真正的对话挪到 boundedElastic 线程：先查语义缓存，多轮和时效性问题绕过，命中就分块回放；未命中走 ChatClient——系统提示词 + 历史 + 注入了当前时间和用户坐标的消息，挂五个地点工具，userId 走 ToolContext 传给工具防越权，用非流式 call() 拿完整回答，这是官方对 Spring AI 流式加工具调用缺陷的 workaround。工具内部做空间约束检索：bbox 粗筛、Haversine 精算、pgvector 语义 Top-K。回答写缓存、写会话记忆、记指标，再按 30 字一块流式回放给前端；客户端断开就 dispose 订阅，不让 LLM 白烧 token。"

#### ⚠️ 卡壳点
① 顺序不能乱：限流/护栏在开 SseEmitter **之前**（请求线程，SecurityContext 可用）；② 伪流式必须主动带上"官方 workaround + issue 编号"，否则必被追问"为什么不用 stream()"；③ 防越权说的是 ToolContext，不是提示词。

## R2 · AI 核心：RAG

### 4. 为什么 AI 助手默认关闭、做成独立模块？（原 Q3 · 🟠）
**考察**：「独立模块 + 配置开关」铁律（风险隔离意识）

#### 标准参考答案（基于代码）
动机：AI 是**外部付费依赖**（DashScope 的 LLM + embedding），可用性与成本都不受我控制，而主功能（地图/打卡/分享）是确定性的自有业务——不能让主功能被一个外部 API 绑架。所以 `AssistantProperties.enabled` **代码默认值就是 false**（README 关键开关 `ASSISTANT_ENABLED` 默认 false），关闭即纯平台，开启才上线 AI。

实现是**两层机制，缺一不可**：
1. **Bean 层**：`assistant` 包内所有组件挂 `@ConditionalOnProperty(prefix="app.assistant", name="enabled", havingValue="true")`——Controller、ChatService、RetrievalService、RateLimiter、Guard、SemanticCache、ExplorerTools、PoiEmbeddingRepository 全部在内。关闭时一个 Bean 都不装配，接口直接 404；
2. **自动配置层**：`AssistantAutoConfigureExclusionEnvironmentPostProcessor`（SB4 新包 `org.springframework.boot`）在开关关闭时**动态排除 6 个 OpenAi\*AutoConfiguration**（Chat/Embedding/Image/AudioSpeech/AudioTranscription/Moderation），并合并已有的 `spring.autoconfigure.exclude`。为什么必须有这层：自动配置不走我的 `@ConditionalOnProperty`，只要 spring-ai-openai 在 classpath 且配了 `spring.ai.openai.api-key`，它就会装配并校验连接。早期用 api-key 占位串 `disabled-when-assistant-off` 规避，是 hack；EPP 是**按开关条件化的排除**（比 `@SpringBootApplication(exclude=...)` 静态排除灵活），且 EPP 时机早于 autoconfigure，注册在 `META-INF/spring.factories`。

效果：关闭 = api-key 可空、主功能零侵入、一键回退纯平台（方案 §13）。

#### 预埋追问逐条拆解
① **@ConditionalOnProperty 怎么实现整体回退**：所有 Bean 同前缀同开关，false 时条件不满足整体不注册；Controller 不存在所以是 404 而非 403/500——不是权限拒绝，是功能不存在。
② **关闭时 autoconfigure 为什么还会装配**：自动配置由 Spring Boot 的 autoconfigure 机制驱动，不看我的业务开关；classpath 有依赖 + 有配置属性就触发。所以光加 @ConditionalOnProperty 不够，必须在自动配置生效前（EPP）把 OpenAi\* 六个类塞进 exclude 列表。迁移 SB4 时这类的包名从 `boot.env` 挪到 `boot`，spring.factories 的 key 不同步改就静默失效（踩坑实录）。
③ **AI 挂了主功能受影响吗**：分两档。运行期 LLM/工具报错：ExplorerTools 每个工具 catch 异常返回自然语言错误串（"推荐地点时出错了"），模型能优雅兜底，对话不中断，同时上报 `assistant.tool.errors` 指标；整体下线：改回 `enabled=false` 重启，全部 Bean 消失，主功能无任何感知。
④ **代价**：条件装配是字符串约定，前缀拼错无编译期检查、静默失效；开关两态 = 两套代码路径，测试矩阵翻倍；EPP 属冷门扩展点，协作认知成本；模块仍同进程，做不到资源级隔离（LLM 阻塞调用只隔离到 boundedElastic 线程池）——真要硬隔离就得拆服务。

#### 🎤 面试版总结（可直接背）
"因为 AI 是外部付费依赖，可用性不受我控制，而主功能是确定性自有业务，不能被它绑架。所以做成默认关闭的独立模块，两层机制：一层是 assistant 包所有 Bean 挂 @ConditionalOnProperty，开关关闭时整体不装配，接口 404；另一层更关键——Spring AI 的自动配置不看我的开关，只要依赖在 classpath 就会装配，我用 EnvironmentPostProcessor 在自动配置生效前动态排除六个 OpenAi 自动配置类，取代了早期 api-key 占位串的 hack 做法，关闭时 api-key 都可以不配。AI 挂掉分两档兜底：单次工具失败返回自然语言错误让模型优雅降级，整体下线改开关重启、主功能零感知。代价是条件装配靠字符串约定容易静默失效，且同进程做不到资源级硬隔离，要硬隔离就得拆服务。"

#### ⚠️ 卡壳点
两层机制必须说全：@ConditionalOnProperty 只管"我的 Bean"，**EPP 才管"自动配置"**——只说前者必被追问②（占位串 hack）打脸。

### 5. 空间约束 RAG 三段式（bbox→Haversine→pgvector）怎么工作？（原 Q7 · 🔴P0）⭐核心亮点
**考察**：地图域 RAG 的真懂

#### 标准参考答案（基于代码）
`AssistantRetrievalService.search(query, lat, lng, radiusOverride)` 五步（默认半径 **3000 米**、Top-K **10**，`AssistantProperties.Retrieval`）：

1. **边界框预过滤**：`GeoUtils.calculateBounds(lat, lng, radius/1000)`（注意该方法半径单位是**千米**，米要 /1000）→ `POIRepository.findWithinBounds`，JPQL 就是 `latitude BETWEEN :minLat AND :maxLat AND longitude BETWEEN :minLng AND :maxLng`——复用地图模块既有查询，普通索引即可；
2. **Haversine 精确过滤**：边界框是半径圆的**外接正方形**，四角超出真实半径；对框内每个点用 `GeoUtils.haversineMeters` 算精确距离，`distance <= radiusMeters` 剔除圆外的点，**同时把精确距离留下来**供结果回传（工具输出里"距你约 X 米"就是它）；
3. **问题向量化**：`embeddingModel.embed(query)`——必须与 POI 入库**同模型**，向量空间才一致；
4. **候选集内语义 Top-K**：`PoiEmbeddingRepository.findSimilar`，SQL `WHERE poi_id IN (圆内ids) ORDER BY embedding <=> ?::vector LIMIT ?`，余弦距离升序（score = 1 − distance），**限定在圆内 id 集合**做近邻，不是全局 ANN；
5. **组装**：回查候选 POI + 复用第 2 步已算的距离。

存储侧：`poi_embedding` 表 `embedding vector(1024)`（对齐 DashScope **text-embedding-v4**），HNSW **vector_cosine_ops** 余弦索引；`poi_id` 唯一约束支撑 POI 增改时 upsert 刷新向量。

#### 预埋追问逐条拆解
① **为什么不能直接纯语义检索**：全局 ANN 回答的是"全库谁最像"，而地图场景用户问的是"**附近**哪里有"——"近"是硬约束不是偏好。纯语义会把三公里外甚至另一城区语义最像的点排前面。所以先空间围栏保证"近"这个不可协商条件，语义只负责在围栏内排"相关"。
② **三段各自过滤掉什么**：bbox 滤掉外接正方形之外的点（普通索引快速收窄，代价是多捞了四角）；Haversine 滤掉框内但圆外的四角点（把方形修成圆，顺带产出精确距离）；pgvector 在幸存者里滤掉语义不相关的、按相关度取 Top-K。
③ **候选集空了怎么办**：`within.isEmpty()` 时在 **embed 之前短路**（省一次 embedding 调用），log.info 记录后返回 `RetrievalResult(query, 0, List.of())`——空结果不是异常；上层工具把它转成自然语言"该范围没找到，建议扩大范围或换关键词"，让模型引导用户。只有 embed 调用失败才向上抛，由护栏层统一兜底。
④ **和"先用 ST_DWithin 再向量"的区别**：功能等价（都是先空间后语义），区别是工程路径。ST_DWithin 是 PostGIS 地理函数，走 GiST 空间索引，要求地理类型列；我用的是既有 lat/lng 数值列 + 既有的 BETWEEN 查询，**复用地图模块同一套索引与查询，不引入第二套地理索引体系**。精度损失由 Haversine 第二段补齐——甚至更精确，直接算出真实距离。这是刻意的复用权衡，不是不会 PostGIS（项目本来就装着 PostGIS + Hibernate Spatial）。

#### 🎤 面试版总结（可直接背）
"我的检索是'先地理围栏、再语义排序'三段式。第一段边界框预过滤：用经纬度 BETWEEN 查询复用地图模块既有索引，把候选快速收窄到半径外接正方形内；第二段 Haversine 精算：框是方形、需求是圆，逐点算精确距离剔除四角圆外的点，距离顺手留下来回传给用户；第三段才做语义：把用户问题向量化，在圆内候选的 id 集合里做 pgvector 余弦 Top-K。为什么不能纯语义？因为'附近'是硬约束不是偏好，纯全局 ANN 会把三公里外语义最像的排前面。默认三公里、Top-10，向量 1024 维对齐 text-embedding-v4，HNSW 余弦索引。候选为空就在 embed 之前短路返回空结果，让模型引导用户扩大范围。没用 ST_DWithin 是刻意的——复用既有 BETWEEN 查询和索引，不引入第二套空间索引体系，精度由 Haversine 段补齐。"

#### ⚠️ 卡壳点
① 顺序是"先几何后语义"，理由一句话：**"近"是硬约束，语义只是围栏内排序**；② 空候选在 embed 之前短路（省钱细节）；③ 别把 bbox 段说成 ST_DWithin——被问区别就答"复用既有查询，Haversine 补精度"。

### 6. 你的 RAG 和通用 RAG 有什么不同？（原 Q12 · 🔴P0）
**考察**：空间约束 RAG 的差异化

#### 标准参考答案（基于代码）
通用 RAG（教程版）：文档切块 → embedding 入库 → 问题向量化 → **全库**向量 Top-K → 拼进 prompt 生成。检索目标是"语料里最相关"，没有业务硬约束。

我的五点差异：
1. **检索范围**：不是全局 ANN，是**候选集内 Top-K**——`findSimilar` 的 SQL 带着 `WHERE poi_id IN (圆内 ids)`。空间围栏先行，语义只在围栏内排序。这是与通用 RAG 的本质区别；
2. **语料粒度**：没有"切块"这一步，POI 天然一条一记录（名称+类别+简介拼成 content）；`poi_embedding.poi_id` 唯一约束，POI 增改时 upsert 增量刷新向量，不存在全量重嵌入；
3. **距离是第一公民**：Haversine 精确距离随结果回传，系统提示词明确要求"数量与距离必须与工具返回完全一致"，工具输出同时给相关度和距离（"相关度 0.87，距你约 350 米"）；
4. **RAG 之上是 Agent**：检索不直接拼 prompt，而是封装成 `@Tool`（recommendNearbyPlaces），由 LLM 自主决定调不调、与 searchPlaces / planRoute / getUserPreferences 怎么组合；
5. **缓存带地理维度**：语义缓存按 `loc_bucket`（经纬度 %.3f 分桶，约 110 米）隔离——同一个问题换个城市不串味（Q13 展开）。

#### 预埋追问逐条拆解
① **通用 RAG 是什么样的**：如上——切块、全局向量召回、拼 prompt、无业务约束。我的回答第一句就点题："我的语义检索只在空间围栏内做"，而不是"我用了 pgvector"（用什么是实现，不是差异）。
② **空间约束带来什么代价**：(a) 两阶段 = 额外成本：bbox 一次 DB 查询 + 每问一次 embedding 调用（缓存 lookup 还要再 embed 一次），低频对话可接受；(b) IN 子句规模随候选数涨：半径大、POI 密时 placeholders 变多，当前 3 公里/校园量级没问题，城市级要再收窄或改成 SQL 连接；(c) 维度 1024 锁死 text-embedding-v4，换模型必须同步改 `vector(1024)` 表定义并全量重嵌入；(d) 外接方形最多多捞 √2 倍候选，由 Haversine 段消化。
③ **没有地理位置的场景还适用吗**：框架依然成立——把"地理围栏"换成任意业务硬约束（价格区间、类目、权限可见范围、在售状态），模式都是"**硬约束先收窄候选 id 集 → 语义只在候选内排序**"。没有硬约束的场景退化回通用 RAG 即可。本质这是"结构化过滤 + 语义排序"的混合检索，空间只是我的实例化。

#### 🎤 面试版总结（可直接背）
"通用 RAG 是文档切块、全库向量召回、拼 prompt，回答'谁最像'；我的场景用户问的是'附近哪里有'，'近'是硬约束。所以我的核心差异是：语义检索只在空间围栏内做——先 bbox 加 Haversine 把候选收窄到圆内 id 集合，pgvector 只在这个集合里排 Top-K。其他差异：POI 天然一条一记录、没有切块，poi_id 唯一支撑增改时 upsert 增量刷新；精确距离随结果回传且提示词强制模型原样引用；检索封装成工具由 LLM 自主调用，RAG 之上是 Agent；语义缓存还按经纬度分桶，同问题换城市不串味。代价是多一次 embedding 和 bbox 查询、候选集大时 IN 子句要收窄、1024 维绑死嵌入模型。这个框架不绑死地理——把围栏换成价格、类目、权限任意硬约束都成立，本质是结构化过滤加语义排序的混合检索。"

#### ⚠️ 卡壳点
差异化的第一句话必须是"**语义检索只在空间围栏内做（候选集内 Top-K）**"，不是"我用了 pgvector"；追问②的代价至少说出"每问多一次 embedding 调用"和"维度绑死模型"两条。

### 7. 语义缓存怎么设计的？哪些情况绕过？（原 Q13 · 🟠）

#### 标准参考答案（基于代码）

**存储**：PG 表 `assistant_cache`（pgvector），列：`loc_bucket`、`query`、`embedding vector(1024)`、`response`、`created_at`；两个索引：HNSW（`embedding vector_cosine_ops`）+ `idx_assistant_cache_bucket_time(loc_bucket, created_at)`。实现类 `AssistantSemanticCache`，在 `AssistantChatService.stream` 里"先查缓存、命中回放；未命中走 Agent、完成后写回"。

**键设计（核心）**：不是精确 key，而是 **(地理桶 + 语义相似)** 双条件：
- `loc_bucket = String.format("%.3f,%.3f", lat, lng)` —— 坐标保留 3 位小数 ≈ **110 米网格**。太粗（%.2f≈1.1km）会把远处问题混进同桶，太细（%.4f≈11m）命中率骤降；110m 与"附近推荐"的空间粒度匹配。
- 桶内按语义找：`WHERE loc_bucket = ? AND created_at >= now() - (?||' seconds')::interval ORDER BY embedding <=> ?::vector LIMIT 1`，再判 `1 - 余弦距离 ≥ 0.95` 才算命中。
- 效果：**语义等价的不同问法也能命中**（"附近有什么好吃的" ≈ "周围有什么美食推荐"），这是语义缓存相对精确缓存的价值。

**三层绕过**：
1. **总开关**：`app.assistant.cache.enabled`（默认 true）。
2. **多轮一律绕过**：`cacheable = history.isEmpty() && isCacheable(message)` —— 有历史就不查不写。理由：同一句话在不同上下文含义完全不同（"这个""远一点"），缓存按单条 query 匹配，多轮场景必答非所问；**只对无上下文的首轮走缓存**。
3. **时效正则**：`TIME_SENSITIVE_PATTERN`（几点|几号|时间|日期|今天|明天|昨天|现在|当前|星期|礼拜|周X|天气|气温|温度|新闻|股价|汇率|比分）命中则绕过——否则"现在几点"会被缓存 24 小时重放旧时间。设计取向：**宁可漏缓存（多花一次 LLM 调用），不可错缓存（答错基本事实）**。

**命中后的处理**：指标 `assistant.chat.cache` 打 hit/miss/bypass 三种 tag；命中**仍把 user/assistant 两条 append 进会话记忆**（多轮连续性不因缓存断链）；回答按 `CACHE_REPLAY_CHUNK=30` 字/块 Flux 回放，前端"流式"体验不变。

**防膨胀**：TTL（默认 86400s=24h）只在查询 SQL 里过滤，过期行仍物理存在 → `@Scheduled evictExpired` 每 **1 小时**物理 DELETE（首轮延迟 60s 避开启动高峰）。

**fail-open**：lookup/put/清理三处全 try/catch 只记日志——缓存故障 = 视为未命中，主链路照走。

#### 预埋追问逐条拆解

- **① 地理分桶 %.3f,%.3f 精度多少？** → 0.001° 纬度 ≈ 110 米（经度随纬度略收窄），即 110m 网格。选型逻辑：与"附近推荐"语义半径同量级。
- **② 时效性问题怎么识别？** → 关键词正则启发式，覆盖时间/日期/天气/新闻/行情/比分六类。漏网风险存在（没写到的时效问法可能被缓存），由 24h TTL 兜底；整体取向是保守绕过。
- **③ 多轮请求为什么跳过？** → 缓存 key 是单条 query 的语义，没有上下文维度。"远一点"在缓存库里永远匹配不到正确答案，只会匹配到某个固定 query 的旧答案——答非所问比慢更糟。
- **④ 缓存击穿/膨胀怎么处理？** → 膨胀：定时物理删除 + 查询侧 TTL 过滤双保险。"击穿"在这里不是经典问题：key 不是热点精确 key 而是 (桶, 语义近邻)，miss 的代价只是一次 LLM 调用且天然自愈（下一个人写入后又可命中）；真正要防的是**错误命中**，靠 0.95 高阈值保守控制。
- **⑤ fail-open 的风险？** → 缓存层故障时退化为"每问都打 LLM"：成本上升、延迟上升，但功能不损——缓存不放大故障。可观测的代价是 put 静默失败会让命中率缓慢下降，靠 `cache miss` 指标监控。
- **边界认知（加分项）**：跨用户共享的前提是"回答不含个性化信息"。M7 引入 getUserPreferences 后，宽泛 query 的回答可能带个人偏好色彩，理论上存在轻微串扰——严格做法是"调用过偏好工具的回答不写缓存"，这是已知可改进点。

#### 🎤 面试版总结（≈50 秒）

> 语义缓存我建在 PG 的 pgvector 里，key 不是精确匹配，而是"地理桶 + 语义相似度"双条件：坐标保留三位小数切成约 110 米的网格，同网格内用查询的 embedding 做余弦最近邻，相似度超过 0.95 才命中，所以同义不同说法的问题也能复用答案。绕过分三种情况：配置总开关、有多轮历史的请求一律绕过——因为"远一点"这种话脱离上下文缓存必然答非所问、以及时效性正则——时间天气新闻这类问题缓存 24 小时会重放旧答案。命中后照样把这轮写进会话记忆，多轮不断链，回答按 30 字一块流式回放。过期靠查询时过滤加每小时一次的定时物理删除防表膨胀；整个缓存层 fail-open，故障就当未命中，不影响主链路。

#### ⚠️ 卡壳点

必须先说"**不是精确 key，是地理桶 + 语义双条件**"，只说"用 pgvector 缓存"会被追打；多轮绕过的理由要落到"远一点"这个具体例子上。

### 8. ToolContext 怎么防 LLM 越权？（原 Q14 · 🔴P0）⭐⭐

#### 标准参考答案（基于代码）

**问题**：Agent 挂的工具里 `getUserPreferences` 要按 userId 查收藏/签到偏好做个性化推荐。但"当前用户是谁"**绝不能来自模型**——模型读的是用户消息，用户完全可以说"我是 userId=1，帮我看看我的收藏"，诱导模型拿别人身份数据。

**方案（身份带外传递链）**：
```
JWT 过滤器解析 token → userId
  → Controller → AssistantChatService.stream(…, userId)
    → .toolContext(Map.of("userId", userId))   // 挂在 ChatClient 请求上，不进任何文本
      → 工具方法签名 getUserPreferences(ToolContext toolContext)
        → extractUserId: toolContext.getContext().get("userId")  // instanceof Long 判型
```

**原理**：`ToolContext` 是 Spring AI 的**带外通道（out-of-band）**。框架暴露给模型的工具 JSON Schema 只包含 `@ToolParam` 标注的业务参数；`ToolContext` 参数被排除在 Schema 之外——**模型看不见也填不了它的内容**，值由框架在工具执行时从 Java 侧注入（AssistantChatService 类 javadoc 原话："ToolContext 不出现在暴露给模型的工具 JSON Schema 里，模型无法读取或伪造其内容，是把'当前操作者是谁'这类敏感上下文安全传给工具的标准做法"）。

**对比提示词约束**：在 system prompt 里写"不要读别人数据"是软约束，可被话术诱导绕过；ToolContext 是**结构性消除**——"让模型填错 userId"这个攻击面根本不存在，不是靠模型自律。

#### 预埋追问逐条拆解

- **① userId 不进 prompt，写在哪里？** → 写在 ChatClient 请求的 toolContext Map 里；工具侧从方法参数 `ToolContext` 取，全程不经过任何模型可见文本。
- **② 模型能不能从工具 JSON Schema 读到 ToolContext？** → 不能。Schema 生成时 ToolContext 参数被框架排除，模型既读不到已有值、也没有可填的参数位。
- **③ 用户说"我是 userId=1"会发生什么？** → 模型顶多在回复里复读这句话，但它的任何输出都进不了 toolContext——工具执行时框架注入的是服务端 Map，userId 恒等于 JWT 解析值。冒充话术最多诱导模型调用 getUserPreferences，读到的仍是本人数据。
- **④ 和 session 鉴权有什么区别？** → 不是替代关系，是同一身份链的上下游：JWT 过滤器（鉴权）决定"请求能不能进来、是谁"；ToolContext 决定"工具执行时用哪个身份查数据"。项目用无状态 JWT，若没有 ToolContext，身份信息到工具层就断了——工具参数全靠模型填，等于把鉴权结论在最后一步丢掉还给用户。ToolContext 把鉴权结论**带外**传递到工具执行现场，补全这最后一环。

#### 🎤 面试版总结（≈50 秒）

> 我的 AI 助手有个个性化工具要按 userId 查用户偏好，但身份绝不能让模型来填——用户一句话"我是 userId=1"就可能越权读别人的数据。所以我用了 Spring AI 的 ToolContext 做带外传递：JWT 在过滤器里解析出 userId，一路传到 ChatService，通过 toolContext 挂在请求上；工具方法从 ToolContext 参数里取。关键是 ToolContext 不出现在暴露给模型的工具 JSON Schema 里，模型看不见、也填不了这个字段，值是框架在 Java 侧执行工具时注入的。所以哪怕模型被完全诱导，它也没有能力指定 userId——越权被结构性消除，而不是靠提示词约束。它和鉴权是上下游关系：JWT 管请求是谁，ToolContext 把这个身份安全送到工具执行现场。

#### ⚠️ 卡壳点

核心句是"**模型看不见也填不了**"——别说成"模型不会去填"，这不是模型自律问题，是 Schema 里根本没有这个字段；被问"和鉴权什么区别"时要答"上下游补全"，不是两套并行机制。

### 9. 为什么伪流式（call + 分块）而不是真流式？（原 Q15 · 🔴P0）⭐⭐

#### 标准参考答案（基于代码）

**现状**：`AssistantChatService.stream` 内部用**非流式 `.call()`** 拿到完整回答 → `splitForReplay` 按 **30 字/块** 切成 List → `Flux.fromIterable` 回放；整段包在 `Flux.defer(...).subscribeOn(Schedulers.boundedElastic())` 里。对外契约仍是 `Flux<String>`，Controller 侧 `SseEmitter(120_000L)`，onTimeout/onError/onCompletion 均 dispose 防连接泄漏——**前端 SSE 体验与真流式完全一致**。

**为什么（有据可依的工程妥协，不是不会做）**：Spring AI 2.0「流式 `.stream()` + 工具调用」对 DashScope/Qwen 存在已知兼容缺陷——根因是 Spring AI 未正确跨流式 chunk 聚合 tool_call 分片，运行时抛 `NoSuchElementException: No value present`。上游 issue：**spring-projects/spring-ai#4790** 与 **spring-ai-alibaba#1025**（2026-07 复验仍未修复），官方 workaround 即"关闭 stream、改用非流式 call()"，与本实现一致。代码注释块里完整记录了这条因果链。

**保住的东西**：Agent + Tool Use 完整保留（工具调用在非流式链路下稳定）；RAG 检索、语义缓存、多轮记忆全部不受影响；前端 fetch + `getReader()` 逐块渲染照常。

**boundedElastic 为什么必要**：`.call()` 是**阻塞** HTTP 调用，若在请求线程（Tomcat worker）直接执行会占死线程；`Schedulers.boundedElastic()` 是 Reactor 专为包装阻塞任务设计的调度器（默认 10×CPU 线程 + 100k 队列），把阻塞调用隔离到弹性线程池，不拖垮请求吞吐。

**切回路径**：上游修复后只需改 stream() 方法内部——call 换回 stream、去掉 30 字分块；对外 Flux\<String\> 与前端 SSE 契约零改动，平滑切换。

#### 预埋追问逐条拆解

- **① 真流式首字延迟低，你不想要吗？** → 想要，但"功能可用" > "首字延迟"：stream()+tools 在 DashScope 上直接抛异常，真流式完全不可用。且我的场景 LLM 中间要调工具（RAG 检索 + 工具执行本身占时间），真流式的首字优势会被工具阶段吃掉一部分，伪流式的体验损失进一步缩小。
- **② NoSuchElementException 根因？** → Spring AI 流式模式下未正确跨 chunk 聚合 tool_call 分片，聚合处 Optional 为空直接 get 抛出。
- **③ issue 号？** → spring-ai 主仓 **#4790**，spring-ai-alibaba **#1025**（都已附在代码注释里，含验证日期）。
- **④ 什么时候能切真流式？** → 上游版本修复该缺陷后：只改 stream() 内部实现，接口契约和前端零改动；属于预留好的演进点。
- **⑤ boundedElastic 为什么必要？** → 见标准答案第 4 段：阻塞调用不能占请求/事件循环线程。
- **前端侧补充**：浏览器原生 EventSource 只能 GET、无法带 Authorization 头，所以前端用 **fetch + ReadableStream 手动消费 SSE**；请求 Accept 同时带 `text/event-stream, application/json`——controller 卸载/异常时 @ExceptionHandler 只能返回 JSON 错误体，若 Accept 仅限 SSE 会触发 406 内容协商失败，前端反而拿不到 404 降级信号。

#### 🎤 面试版总结（≈50 秒）

> 我的前端是标准 SSE 打字机效果，但后端其实是"伪流式"：用非流式 call 拿完整回答，按 30 字一块用 Flux 回放。原因很具体：Spring AI 2.0 的流式 stream 加工具调用，在 DashScope 上有已知缺陷——跨流式分片聚合 tool_call 失败，直接抛 NoSuchElementException，官方 issue 是 spring-ai#4790 和 spring-ai-alibaba#1025，官方 workaround 就是改用非流式 call，所以这是有据可依的工程妥协。我保住了核心的东西：Agent 和工具调用完整可用、前端体验不变；阻塞的 call 放到 boundedElastic 线程池执行，不占请求线程。上游修复后我只改一个方法就能切回真流式，对外契约零变动。

#### ⚠️ 卡壳点

顺序不能反：**先说"官方 workaround + issue 号"，再说分块回放**——先讲实现会被追"你是不是不会真流式"；issue 号 #4790/#1025 必须能脱口而出，这是"真踩过坑"的硬证据。

### 10. 为什么 PostGIS + pgvector 双扩展，不单独上向量库？（原 Q6 · ⚪）

#### 标准参考答案（基于代码）

**三条主线**：
1. **数据本来就在 PG**：POI 主数据、空间属性、向量语料同库。我的检索是"bbox 预过滤（JPQL）→ 候选集内 pgvector Top-K"两段，都落同一个 PG——**不需要把候选 ID 跨服务搬运**，也没有"业务库与向量库双写一致性"问题。
2. **量级不匹配**：Milvus/Qdrant 的核心优势是亿级向量、分布式分片、高性能标量+向量混合过滤。本项目 POI 是城市级目录、万级以内，pgvector + HNSW 索引绰绰有余——专用向量库在这个量级是负资产。
3. **运维成本**：项目是单体 + docker compose 一键编排（README 部署方式）。多一个独立向量库 = 多一个有状态服务：部署、备份、监控、版本升级全要单独管；复用 PG 则备份恢复一套、监控一套（Prometheus 既有）。

**代价/坑（主动交代）**：
- **镜像坑（已解决）**：官方 `postgis/postgis` 镜像只含 PostGIS 不含 pgvector，直接 `CREATE EXTENSION vector` 失败。解法见追问③。
- **资源争用**：HNSW 索引驻内存，与 PostGIS 空间索引、业务查询共享 PG 的 buffer pool/内存，量级上来需要权衡调参。
- **版本耦合**：PG 大版本升级时要同时验证两个扩展的兼容性，比单扩展多一层回归。

#### 预埋追问逐条拆解

- **① Milvus/Qdrant 考虑过吗？** → 考虑过，排除理由就是上面三条：事务割裂、量级不匹配、运维成本。**切换条件**明确：向量规模到千万级、或检索延迟 P99 不可接受、或需要复杂混合过滤时再上专用库——因为检索层已收敛在 `PoiEmbeddingRepository` 一个类里，替换成本可控。
- **② 一个 PG 同时管空间+向量有什么坑？** → 镜像坑（已解）、HNSW 内存与既有负载争资源、扩展版本耦合升级。另外注意：本项目空间预过滤实际用的是 **JPQL BETWEEN 边界框 + Haversine 精算**（复用地图既有查询），PostGIS 主要用在空间列/空间索引上——不是所有空间需求都压给 PostGIS。

#### 🎤 面试版总结（≈50 秒）

> 选 PG 双扩展而不是独立向量库，核心理由三条：第一，业务数据和向量本来就在同一个 PG，我的 RAG 检索是先 bbox 预过滤再候选集内向量排序，两段都在同一个库，没有跨库一致性问题；第二，我的 POI 是城市级目录、万级以内，pgvector 加 HNSW 完全够，Milvus 那种亿级分布式能力在这里是负资产；第三，单体加 compose 一键编排，多一个有状态服务就多一整套部署备份监控。踩过的坑是 postgis 官方镜像不带 pgvector，我自建了数据库镜像，基于 postgis 镜像用 apt 预编译包装上 pgvector。真到千万级向量或延迟不可接受，检索层收敛在一个仓储类里，随时可换。

### 11. poi_embedding 表为什么不交给 JPA 管，而用 JdbcTemplate？（原 Q9 · ⚪）

#### 标准参考答案（基于代码）

**根因：Hibernate 类型系统不认识 pgvector 的 vector 列类型**——没有对应的 Java 类型映射和 dialect 方言（javadoc 原话："vector 列 Hibernate 不识别（方案 §6.1）"）。如果硬给 entity 加 embedding 字段：`ddl-auto=validate` 下**启动期校验直接失败**；即便绕过校验，运行期 JDBC 也无法把 `float[]` 绑定成 vector 类型的参数（PG 端报类型错误）。

**解法**：`PoiEmbeddingRepository` 用 `@Repository + JdbcTemplate` 原生 SQL，整张表完全由 SQL 脚本（`02-pgvector.sql`）建，不进 JPA 实体体系：
- 写入（upsert）：`INSERT … VALUES (?,?,?::vector,now()) ON CONFLICT (poi_id) DO UPDATE …`——参数以 `"[v1,v2,...]"` 文本字面量传入（`toVectorLiteral` 把 float[] 拼成文本），PG 端 cast 成 vector；`ON CONFLICT` 原生 upsert 支撑增量刷新。
- 检索（findSimilar）：`1 - (embedding <=> ?::vector) AS score` + 动态 IN 占位符 + `LIMIT ?`——余弦算符 `<=>`、`ON CONFLICT` 这些原生能力 JPA @Query 要么写不了要么极其别扭。

**`?::vector` 是什么**：`?` 是 JDBC 参数占位符，`::vector` 是 PostgreSQL 的显式类型转换（`CAST(? AS vector)` 的简写）。JDBC 协议层不认识 vector 类型，参数只能当字符串传，由 PG 在 SQL 层把文本 cast 成 vector 类型。

#### 预埋追问逐条拆解

- **① Hibernate 不识别 vector 会怎样？** → 分两阶段：validate 模式下启动就炸（表结构对不上/无法映射）；运行期则是参数绑定失败。所以这张表根本不建 entity，结构完全交给 SQL 脚本。
- **② `?::vector` 什么意思？** → 见上：JDBC 占位符 + PG 显式 cast 简写，等价 `CAST(? AS vector)`。
- **③ 换 ORM 能解决吗？** → **不能，因为这不是 ORM 的问题，是 JDBC 类型映射的问题**：vector 没有标准 JDBC SQL 类型，MyBatis 同样要自定义 TypeHandler 手写 cast；Hibernate 的路线是自定义 UserType（或引入 pgvector-java 官方包提供的 UserType），为一个非 JPA 标准类型写整套适配，不如一层薄 JdbcTemplate SQL 直白。判断标准：**当一张表的核心能力全在方言特性上时，把它隔离成原生 SQL 仓储是成本最低的方案**——项目里只有这一张表如此，边界清晰，不污染其余 JPA 仓储。

#### 🎤 面试版总结（≈45 秒）

> poi_embedding 我特意不交给 JPA，根因是 Hibernate 的类型系统不认识 pgvector 的 vector 列——validate 模式下启动就过不去，运行期 JDBC 也绑不了 float 数组到 vector 参数。所以这张表用 JdbcTemplate 原生 SQL：写入时把向量拼成文本字面量，用问号冒号冒号 vector 的显式 cast 让 PG 在 SQL 层转类型，配合 ON CONFLICT 做增量 upsert；检索用余弦算符加 LIMIT 做 Top-K——这些方言能力 JPA 查询写不了。要强调这不是性能原因，是类型系统原因；换 MyBatis 也一样要手写 TypeHandler，所以最便宜的做法就是把这一张表隔离成原生 SQL 仓储，其余表照常走 JPA。

#### ⚠️ 卡壳点

**别说成"JdbcTemplate 性能更好"**——原因是类型系统不是性能；`::` 是 PG 的 CAST 简写（等价 `CAST(? AS vector)`）要能写出；追问③的关键句"**JDBC 类型映射缺失，换 ORM 也要手写适配**"。

### 12. 限流 + 护栏怎么设计的？为什么 fail-open？（原 Q16 · 🟠）

#### 标准参考答案（基于代码）

**限流（AssistantRateLimiter，Redis 固定窗口）**：`key = assistant:rl:{userId|anon}:{epochMinute}`（`epochSecond/60`），`INCR` 计数，首次（count==1）设 **70 秒过期**（>60s，保证跨窗口残留 key 自动清理）；超过 `perUserPerMin=20` 拒绝（Controller 里 429，**在开 SseEmitter 之前**）。Redis 异常 catch 后**放行**（fail-open），注释原话"避免缓存故障阻断正常对话"。

**护栏（AssistantGuard，纯 Java 无外部依赖）**：①空/空白消息 → 400；②长度 > **500 字** → 400；③**7 条注入启发式正则**（忽略以上指令 / ignore previous instructions / system prompt / developer mode / 开发者模式|越狱|jailbreak / you are now / 忘记无视身份设定）命中 → 400。定位（javadoc 原话）："**工程化的基础防线（轻量启发式），并非绝对安全；与系统提示词约束、工具只返回平台真实数据共同构成纵深防御**"。

**为什么 fail-open（先澄清题面）**：fail-open 的是**依赖外部组件的辅助层**——限流（Redis）、语义缓存（PG）、会话记忆（Redis）；**护栏是纯内存正则计算，没有外部依赖，天然不涉及 fail-open**，命中即拒。fail-open 的判断标准：这一层失效的代价能否被后层兜住——
- 限流失效 = 多付一些 LLM 成本，后面还有 JWT 鉴权门槛（必须是登录用户）、护栏、单机吞吐上限，损失有界；
- fail-closed 的代价 = Redis 一抖，**全部**用户的对话百分百不可用。
- 辅助层的职责是"锦上添花"，不能让它变成主链路的单点故障源。

#### 预埋追问逐条拆解

- **① 固定窗口 vs 滑动窗口？** → 固定窗口：一个 INCR 就够，原子、零 Lua、零额外结构；缺陷是窗口边界突刺（相邻两分钟边界处 40 秒内可能放行近 2 倍配额）。本场景限流目的是**防刷成本不是精确配额**，20/min 的边界毛刺无伤大雅；要平滑可升级 Redis ZSET 滑动窗口或 Lua 脚本，成本略增。
- **② 正则能绕过吗？** → 能，代码注释自己写明"非绝对安全"：同义改写、拼音、插入分隔符都能绕启发式。所以正则只拦"低成本的批量滥用"，不承诺拦"定向高级攻击"——后者靠纵深防御的后两层兜底：系统提示词（11 条规则：不编造地点、不泄露上下文）+ **结构防御**（ToolContext 身份带外不可伪造、工具只返回平台真实数据，被诱导也拿不到敏感外部数据）。
- **③ fail-open 不会导致限流失效吗？** → 会的——Redis 故障期间限流形同虚设，但这是"降级运行"不是"失效事故"：Redis 挂是可观测事件（健康检查/指标），窗口最长 70 秒的 key 修复后自动恢复；期间的成本损失有上限（JWT 登录门槛 + 单机吞吐 + 护栏仍在）。反过来 fail-closed 把小概率基础设施故障放大成全量功能不可用，才是不可接受的。
- **④ 护栏和系统提示词怎么配合？** → 三层纵深：护栏在**请求进模型前**硬拦截（确定性、零成本、可解释、给用户明确 400）；系统提示词在**模型内**软约束（语义级、覆盖面广，防"没被正则拦住的诱导"）；工具层**结构防御**兜底（身份不可伪造 + 数据面收窄）。三层失效模式互不相关，攻击要同时穿透三层。

#### 🎤 面试版总结（≈50 秒）

> 限流是 Redis 固定窗口：按用户加分钟桶 INCR 计数，key 带时间片、首次设七十秒过期自清理，每分钟二十次，超了在开 SSE 之前就拒四二九。护栏是纯 Java：非空、五百字上限、七条注入启发式正则，命中直接四百。fail-open 要先澄清：真正 fail-open 的是依赖 Redis 的限流和依赖 PG 的语义缓存，护栏本身零外部依赖不存在这个问题。fail-open 的判断标准是"这层失效的代价能否被后层兜住"——限流失效只是多付点 LLM 成本，后面还有鉴权、护栏、工具只读；而 fail-closed 会让 Redis 一小抖全部用户不可用，辅助层不能变成单点故障。注入正则确实能绕，代码注释也写明非绝对安全，它和系统提示词、ToolContext 结构防御构成三层纵深。

#### ⚠️ 卡壳点

先澄清"**护栏不是 fail-open，它没有外部依赖**"再往下讲——顺着题面说"两个都 fail-open"会被追打；fail-open 理由必须落到"**辅助层不能变单点故障**"这句。

### 13. 多轮对话记忆怎么存的？（原 Q17 · 🟠）

#### 标准参考答案（基于代码）

**结构**：Redis **List**，`key = assistant:conv:{conversationId}`（conversationId 由前端打开对话面板时生成 UUID），每个元素是 Jackson JSON 编码的 `{role: "user"|"assistant", content}`（内部 record Turn）。读取时解析成 Spring AI 的 UserMessage/AssistantMessage，经 `.messages(history)` 传给 ChatClient——让"这个""再远一点"这类指代性追问结合上文理解。

**写路径（append）三件事原子完成**：
1. `rightPush` 追加一条；
2. `trim(key, -maxEntries, -1)` **只保留最近 maxTurns×2 条**（6 轮问答 = 12 条）——有界环形缓冲，防单会话无限膨胀；
3. `expire` 续期 **30 分钟**——每次追加都续期，活跃会话不过期；30 分钟不说话自动清，**无需显式清理接口**。

**读路径（loadHistory）**：`range(key, -maxEntries, -1)` 取尾部 N 条天然时间正序；conversationId 为空/开关关闭/Redis 异常均返回空列表。

**fail-open**：读写异常只记日志——最坏退化成单轮对话，不是请求失败。且退化后 `history.isEmpty()` 成立，**语义缓存自动重新生效**（首轮逻辑），两层是联动的。

#### 预埋追问逐条拆解

- **① Redis List 还是 Stream？** → List。需求本质是"**有界环形缓冲 + TTL**"：RPUSH+LTRIM 两条命令、内存恒定、语义直白。Stream 为消费组场景设计（多消费者、ACK、Pending 列表、持久消费进度），单会话单读者完全用不上，还占更多内存——用 Stream 是拿大炮打蚊子。
- **② 最近 6 轮怎么截断？** → `maxTurns=6`（一问一答算 1 轮）换算 `maxEntries=12`；**写侧 trim、读侧 range 双重按 12 截断**——写侧防膨胀，读侧保证即使 key 里条目更多也只组装 12 条。
- **③ TTL 30 分钟合理吗？** → 合理且可配置（AssistantProperties）。典型对话轮次间隔远小于 30 分钟；每次 append 续期意味着"活跃会话永不过期、闲置会话自动回收"；30 分钟后回来相当于开新上下文，配合语义缓存首轮命中，退化体验可接受。
- **④ token 爆炸怎么办？** → 三层保护：trim 恒定 12 条上限；护栏 500 字/条限制单条消息体量；maxTurns 可调。12 条 × 数百字 ≈ 数千 token，相对模型上下文窗口有充分余量——token 成本是**常数不是变量**。
- **⑤ fail-open 退化成单轮会怎样？** → loadHistory 异常返回空列表 → 本次请求按无历史处理：不携带上下文（指代类问题可能答不准），但对话本身正常完成；同时因 `history.isEmpty()` 重新满足缓存条件，首轮类问题还能吃缓存。代价是体验降级（失忆），不是功能不可用——这正是 fail-open 的设计意图。

#### 🎤 面试版总结（≈50 秒）

> 多轮记忆用 Redis List 存：按会话 ID 一个 key，每条消息 JSON 编码 user/assistant 角色压栈。写入时三步：追加、LTRIM 只留最近六轮也就是十二条、每次续期三十分钟——等于一个有界环形缓冲，活跃会话不过期、闲置自动回收，不需要清理接口。读取取尾部十二条拼成 Spring AI 的消息列表传给模型，"远一点"这种指代就能结合上文。选 List 不选 Stream，因为需求就是环形缓冲加 TTL，Stream 的消费组能力用不上。防 token 爆炸靠十二条上限加五百字护栏，成本是常数。整层 fail-open，Redis 异常最坏退化成单轮对话，而且退回单轮后语义缓存的生效条件又满足了，两层是联动的。

#### ⚠️ 卡壳点

数字链要说全：**6 轮 × 2 = 12 条，写 trim 读 range 双截断**；TTL 是"**每次 append 续期**"不是到点必清；fail-open 退化时记得点一句"语义缓存重新生效"体现两层联动。

## R5 · MQ + Outbox + 安全（一）

### 14. 为什么用 Outbox 模式，不直接发 MQ（原 Q20 · 🔴P0）

#### ① 标准参考答案（基于真实代码）

直接在业务代码里发 MQ 的本质问题是**双提交**："写业务库"和"发消息"是两个系统上的两个动作，没有共同事务，怎么排顺序都漏：

- **先发 MQ 后写库**：MQ 发成功了、业务写库失败/回滚 → 下游收到一条"幽灵事件"（点赞通知发出去了，点赞根本没落库）；
- **先写库后发 MQ**（更常见的直觉写法）：写库成功后进程崩溃 / MQ 宕机 / 网络抖动，`convertAndSend` 抛异常 → 业务已经回不去了，这条**通知永久丢失**，而且业务接口还会因为发 MQ 失败而 500，把"发通知"这种辅助功能的故障传染给主流程。

Outbox 的解法是把"发消息"降级成"写一行本地数据"：业务事务内**同库写入** `notification_event_outbox`（PENDING=0），和业务写共享同一个 PG 本地事务——**原子性由本地事务天然保证**。之后由独立的投递链路异步补发（`NotificationOutboxDispatcherServiceImpl`）：

- `@Scheduled(fixedDelay=15s)` 扫 PENDING，每批 `batchSize=20`；
- `publisher.publish` 发 RabbitMQ（消息头带 `outboxId`），成功置 SUCCESS=1；失败置 FAILED=2、`attemptCount+1`、`lastError` 截断 500、`nextRetryAt=now+120s`；
- 下一轮同时重试"未超上限且到点"的 FAILED；`attemptCount ≥ maxAttempts=5` 留作死信，走 `AdminNotificationOutboxController` 管理接口人工 `retryEvent`，避免无限重试风暴。

配套两件事：**①无 MQ 降级**——`NotificationEventPublisherImpl` 里 `rabbitTemplate==null` 时（`RABBITMQ_ENABLED=false`）不静默丢弃，同步直调 `NotificationDeliveryService.deliver` 落库，本地开发/无 MQ 部署通知照常可用；**②消费幂等**——at-least-once 必然可能重发（发布成功后、状态更新前崩溃），靠 outboxId 去重兜底（见 #16）。

#### ② 预埋追问逐条拆解

**追问①：直接发 MQ 会丢什么？**
两个方向的丢失都要说全：先发后写库丢的是**一致性**（幽灵事件，通知和业务对不上）；先写库后发 MQ 丢的是**通知本身**（MQ 不可用/进程崩溃时永久丢，除非业务侧写补偿）。另外还有一个隐性问题：发 MQ 失败异常往上抛，主接口跟着失败——辅助功能变单点。

**追问②：Outbox 怎么保证一致？**
核心一句话："把跨系统的原子性问题转化为单数据库的本地事务问题"。业务写和 outbox 写在同一个事务里 commit/rollback，不可能出现"有通知记录没业务"或"有业务没通知记录"；投递是事务提交后异步补的，最终一致（延迟上限≈一个调度周期 15s，失败再退避 120s）。

**追问③：Outbox 的代价？**
四条，主动说出来显得真做过：a) **延迟**——从同步变异步，最多等一个调度周期；b) **表膨胀**——SUCCESS 记录持续累积，需要定期归档清理（项目里目前留作投递审计，没做自动清理，这是可以主动认的改进点）；c) **复杂度**——一套三态状态机 + 调度器 + 重试 + 死信人工处理；d) **轮询成本**——每 15s 打一次 DB（量级小可忽略）。

**追问④：替代方案（事务消息/Seata）？**
- **RocketMQ 事务消息**：半消息 + 本地事务 + 回查，把"本地事务和发消息"绑在一起，是 MQ 原生的 Outbox 平替——但我用的是 RabbitMQ，它没有事务消息语义，硬要上就得换 MQ；
- **Seata AT/TCC**：为一条点赞通知引入 TC 协调器和全局锁，运维成本完全不成比例，通知这种"丢了也能容忍重发"的场景不值得强一致；
- 结论：单体 + PG + RabbitMQ 的组合下，Outbox 是**零额外基建**就能拿到可靠投递的方案，复杂度花在自己可控的代码里而不是新组件上。

#### 🎤 面试版总结

> 直接在业务里发 MQ 是双提交问题：先发后写库会出幽灵事件，先写库后发 MQ 在 MQ 不可用时通知永久丢、还会把主接口拖挂。我用 Outbox 把它转成本地事务问题：业务事务里同库写一条 outbox 记录，原子性由 PG 事务天然保证；再由调度器每 15 秒扫待发表、每批 20 条发 RabbitMQ，消息头带 outboxId。成功置 SUCCESS，失败置 FAILED 退避 120 秒重试，超过 5 次转死信走管理接口人工处理。消费端按 outboxId 幂等去重，配合无 MQ 时同步直发降级，整条链路是 at-least-once 加业务幂等，最终一致。代价是秒级延迟、outbox 表要治理、多一套状态机，但相比引入 RocketMQ 事务消息或 Seata，这是零新增基建的选择。

#### ⚠️ 卡壳点

数字链 15s / 20 条 / 120s 退避 / 5 次上限要顺口；"先发后写丢一致性、先写后发丢通知"两个方向都要说；代价里主动认"SUCCESS 记录没做自动清理"是真做过的味道。

### 15. Outbox 批量调度为什么故意不加 @Transactional（原 Q22 · 🔴P0 ⭐⭐）

#### ① 标准参考答案（基于真实代码）

调度链路的真实结构：`@Scheduled scheduledDispatch()`（15s）→ `this.dispatchPendingEvents()` → 循环 `dispatchSingleEvent(event)` → `publisher.publish`（发 MQ，网络 IO）+ `outboxRepository.save(event)`（状态落库）。批量方法上**故意没有** `@Transactional`，两层原因：

**第一层：加了也不生效。** `scheduledDispatch()` 调 `dispatchPendingEvents()` 是**类内 `this.` 自调用**——Spring 声明式事务是 AOP 代理对象在方法前后 begin/commit 的，自调用走的是目标对象本身，根本不经过代理，拦截逻辑没机会执行。注解贴了是无效的，还会误导后来者以为这里有事务保护。

**第二层：就算让它生效，语义也是错的。** 假如整批 20 条跑在一个事务里：a) **毒丸放大**——第 19 条失败整批回滚，前 18 条 MQ 已经发出去了但状态没置 SUCCESS，下轮全部重发，重复投递被人为放大 20 倍（虽然有幂等兜底，但等于白兜）；b) **事务包网络 IO**——`publish` 是发 MQ 的网络调用，被卷进 DB 事务后，MQ 一慢连接就被长时间占用，连接池耗尽风险；c) 调度任务 15s 一轮，上一轮长事务还没提交下一轮又进来。

**正确姿势（也是代码现状）**：调度方法无环绕事务，每条事件"投递 + 状态更新"通过 `repository.save(event)` **独立提交**——无外层事务时 Spring Data JPA 的 `save` 自带独立事务（`SimpleJpaRepository` 上就有 `@Transactional`），一条失败只脏自己，其它 19 条照常，这正是 Outbox 要的"逐条提交、互不传染"语义。如果未来单条逻辑变重（多表写），把 `dispatchSingleEvent` 抽到独立 Bean 再标 `@Transactional` 显式逐条开。

#### ② 预埋追问逐条拆解

**追问①：@Scheduled 自调用为什么不走代理？**
Spring AOP 的代理模型：容器里注入给别人的是代理对象，事务在代理的拦截器里开；但对象内部 `this.methodB()` 用的是原始目标对象的引用，不经过代理。所以 `scheduledDispatch()` 里调 `dispatchPendingEvents()`，就算后者贴了 `@Transactional` 也是裸调。经典解法是自注入（注入自己的代理）或 `AopContext.currentProxy()`，但这里根本不需要——见②。

**追问②：加了 @Transactional 会发生什么？**
分两段答：贴在 `dispatchPendingEvents` 上 → 被①的自调用绕过，**静默无效**（最危险，看起来有事务实际没有）；贴在 `scheduledDispatch` 上让它生效 → 整批一个事务，一条失败连坐全部回滚 + 已发消息全部重发（毒丸放大），且发 MQ 的网络 IO 拉长事务占连接。两个方向都是错的，所以正确答案是"没有事务 + 依赖 save 的独立事务"。

**追问③：逐条独立提交 vs 批量提交？**
这里逐条独立是**需求**不是妥协：Outbox 的失败单元就应该是一条事件——重试、退避、死信判定都以单条为粒度；批量事务把失败单元扩大到整批，与重试机制的设计粒度直接冲突。批量提交有价值的场景是"一批数据要么全要么无"的写入语义（比如批量导入），投递场景恰好相反。

**追问④：怎么发现的（踩坑 or 经验）？**
诚实版：写第一版时直觉想给批量方法加 `@Transactional` 求"稳"，review 推演失败场景时想清楚了两层问题——自调用让它静默失效、真生效了整批回滚语义还是错——于是删掉并在类注释里写明原因防回归（代码里标注为修复 #5）。这不是线上事故换来的，是"想明白事务代理边界 + Outbox 语义"之后的设计决策，能讲清楚为什么比踩过坑更有说服力。

#### 🎤 面试版总结

> 这是故意的。我的调度方法是 15 秒一轮扫 outbox，循环里每条事件发 MQ 加更新状态。不加事务有两层原因：第一，调度入口内部是 this 自调用，不走 AOP 代理，@Transactional 贴了也是静默无效；第二，就算让它生效，整批二十条跑在一个事务里，一条失败全部回滚，而前十八条消息已经发出去了，状态又变回待发，下一轮全部重发，重复投递被放大，而且发 MQ 的网络 IO 被卷进数据库事务，MQ 一慢连接池就危险。所以正确姿势是批量方法无事务，每条事件靠 Spring Data save 自带的独立事务逐条提交——一条失败只影响自己，这正是 Outbox 逐条重试语义要的失败单元。如果单条逻辑以后变重，我会把它抽到独立 Bean 显式逐条开事务。

#### ⚠️ 卡壳点

两个层次必须分开说：**①静默无效（自调用）②真生效更糟（毒丸放大 + IO 卷进事务）**；`SimpleJpaRepository.save` 自带事务是"逐条提交"的代码依据；别把④说成线上事故——"review 推演发现"更稳。

### 16. 消费端怎么幂等，at-least-once 重复怎么办（原 Q23 · 🟠P1）

#### ① 标准参考答案（基于真实代码）

先说重复从哪来（at-least-once 是设计选择）：a) Dispatcher **发布成功后、save(SUCCESS) 之前**崩溃 → 重启后再发一次；b) MQ broker 在 consumer ack 前挂 → 消息 redeliver；c) 管理接口手动 `retryEvent`。宁可重复、不可丢失。

幂等实现落在 `NotificationDeliveryService.deliver(payloadJson, outboxId)`：

1. **消息头携带 outboxId**：发布器 `convertAndSend` 时 `message.getMessageProperties().setHeader("outboxId", outboxId)`，Listener 从 `@Header` 取出传入；
2. **先查后插**：`deliver` 开头 `notificationRepository.existsByOutboxId(outboxId)`，已存在直接 return（debug 日志跳过）；
3. **数据库唯一约束兜底**：`Notification.outboxId` 上是 `@Column(unique = true)`（首次 DDL 生成时落到 PG 唯一索引）。

两层配合的分工：`exists` 检查挡住**绝大多数**重复（省一次异常开销、日志干净）；唯一索引兜住 **check-then-act 的并发竞态窗口**——同一 outboxId 的两条重复消息被两个线程并发消费、都通过了 exists 检查时，后插入者违反唯一约束抛异常 → 消费失败进重试 → 再进来时 exists 命中 → 跳过。最终效果：**任意次重发，Notification 表最多一条**。

#### ② 预埋追问逐条拆解

**追问①：按 outboxId 去重怎么实现？**
如上三层：消息头传 ID → 消费侧 existsByOutboxId 先查 → 唯一索引兜并发。关键点是把 outbox 记录的主键当成事件的**业务身份**，天然全局唯一且在投递全程不变。

**追问②：数据库唯一约束？**
有，`@Column(unique=true)`。要讲清楚它是**兜底不是主力**：没有它，并发重复时 exists 检查存在竞态会双写；有了它，竞态窗口内的重复以"约束冲突 → 重试 → 跳过"收场。反过来说只有唯一约束没有 exists 预查也能对，但每条重复都走异常栈，浪费且日志脏。

**追问③：幂等的代价？**
a) 每条消息多一次 exists 查询（通知量级下可忽略）；b) 唯一索引轻微写放大；c) "先查后插 + 异常重试"的代码和理解成本；d) 极端并发下重复消息要多走一轮重试才被拦下。换来的是任意重发不产生脏数据——这笔账在"通知"场景稳赚。

**追问④：exactly-once 为什么不用？**
因为**消费位移在 MQ、业务数据在 PG，两个系统无法共享一个原子事务**——"落库"和"ack"不可能原子完成，除非上 XA/两阶段（性能差、复杂度高）或换支持事务消息语义的 MQ。业界标准做法就是 at-least-once 传输 + 消费端业务幂等，落库效果等价于 exactly-once，成本低一个量级。而且本场景重复的代价只是"多一条站内通知"，天然适合这套。

#### 🎤 面试版总结

> 我的投递链路是 at-least-once：发布成功后状态更新前崩溃、broker 在 ack 前宕机、人工重试，都会造成重复，这是宁可重复不可丢失的设计选择。幂等靠 outboxId：发布时把 outbox 主键塞进消息头，消费落库前先 existsByOutboxId 查一道，已有就跳过；同时 Notification 表的 outboxId 列建了唯一约束，兜住并发场景下先查后插的竞态窗口——冲突的那条走异常重试，再进来就被 exists 拦住。所以任意次重发表里最多一条。代价是每条多一次查询和一点索引开销。不用 exactly-once 是因为位移在 MQ、数据在 PG，两边没法原子提交，业界通行做法就是 at-least-once 加消费幂等，效果等价成本更低。

#### ⚠️ 卡壳点

先说**重复的三个来源**再讲方案（显得懂 at-least-once）；**exists 是主力、唯一约束兜并发竞态**这个分工别讲反；追问④核心句"位移和业务数据在两个系统，无法原子提交"。

### 17. JWT revoke_before 黑名单 + 1 秒宽限（原 Q25 · 🟠P1 ⭐）

#### ① 标准参考答案（基于真实代码）

JWT 是无状态的，验签只证明"这个 token 是我签的、没过期"，不经过任何服务端状态——所以吊销必须引入服务端共享存储，把校验从"验签通过"升级为"**验签通过 且 签发时间不早于该用户的吊销线**"。

**写侧（四处安全闭环）**：`logout` / `changePassword` / `resetPassword`（用户主动三条链）+ 管理员禁用用户（`AdminUserServiceImpl`，同时清用户缓存，详见 #19）都执行同一个动作——`SET jwt:revoke_before:{userId} = System.currentTimeMillis()（毫秒）`，TTL = token 有效期秒数 + 60s（**比最长寿的 token 活得久**，所有旧 token 自然过期后这条记录也自动清掉，不留垃圾），同时删 `user:info:{userId}` 缓存。语义：**此时刻之前签发的该用户所有 token 一次性全部作废**——登出踢当前设备顺手全踢，改密/找回密码必须全踢（否则被盗号用户改回密码后，攻击者的旧 JWT 在剩余有效期 内还能继续访问，这是找回密码也写 revoke_before 的原因）。

**读侧（`JwtAuthenticationFilter`）**：token 验签通过后 GET `revoke_before`，若 `iat < revoke_before - 1000` 则不设置认证直接放行到后续授权（最终 401）。注意实现细节：被吊销不主动写 401，只是视为"没带 token"。

**1 秒宽限的由来**：JWT 的 `iat` 精度只到**秒**（`getIssuedAt().getTime()` 已截断到整秒），而 revoke_before 是完整**毫秒**。误杀场景：登出时刻 T（毫秒）后同一秒内重新登录，新 token 的 iat 被截断到整秒 ≤ T——若吊销条件是不减宽限的 `iat < T`，这个**新** token 会被误判已吊销，用户重登后仍然 401。减去 1000ms 后条件变为 `iat < T - 1000`，同秒签发的新 token iat ≥ T-1000，放行。代价：T 之前 1 秒内签发的旧 token 最多多活 1 秒，安全影响可忽略——用 1 秒的吊销精度损失换掉误杀，值得。

#### ② 预埋追问逐条拆解

**追问①：JWT 无状态怎么吊销？**
无状态的本质是校验不依赖服务端会话，吊销就必然要破坏"无状态"——引入共享状态。方案谱系：token 黑名单（存 jti）、用户级时间戳（revoke_before）、token 版本号（用户表存版本、JWT 携带、比对）。我选时间戳方案，理由见④。

**追问②：revoke_before 存什么？**
一个毫秒时间戳，key 按用户维度 `jwt:revoke_before:{userId}`。存储 O(1)——一个用户一条，不随登出次数/token 数膨胀；TTL 设为 token 最长寿命+60s，到期自动清。

**追问③：1 秒宽限不加会怎样？**
就是"登出后同秒重登被误杀 401"：iat 秒级 vs revoke_before 毫秒级，同秒新 token 的 iat 必然 ≤ 登出毫秒值，严格小于判断会把它当旧 token 吊销。这是个**单位精度不对齐**的隐蔽 bug，出在现场是"我明明重新登录了怎么还是 401"这种极难排查的用户投诉。

**追问④：和 token 黑名单（存具体 token）比？**
黑名单登出只吊销当前 token，别的设备不受影响（粒度细是优点）；但 a) 每次登出存一条，**存储随登出次数线性膨胀**；b) "改密踢所有设备"这个刚需黑名单做不到——服务端根本不知道该用户手上有哪些 token；c) TTL 要按每个 token 的剩余寿命逐条算。revoke_before 一个 key 天然全量吊销、O(1) 存储、TTL 好算，和"登出全踢 + 改密必全踢"的安全语义严丝合缝。若业务将来要求"登出只踢当前设备、改密才全踢"，再演进为 jti 黑名单 + revoke_before 双轨。

#### 🎤 面试版总结

> JWT 无状态验签是可篡改不可吊销的，所以我在登出、改密、找回密码三处都会往 Redis 写一个用户级的 revoke_before 毫秒时间戳，TTL 设成 token 最长寿命加六十秒，语义是这个时刻之前签发的所有 token 全部作废。过滤器里验签通过后再比对：签发时间早于吊销线减一秒才拒绝。这一秒宽限是必须的：JWT 的 iat 只到秒、revoke_before 是毫秒，不放宽限的话，登出后同一秒内重新登录的新 token 会被误判吊销，用户重登还是 401。和存具体 token 的黑名单比，revoke_before 一个用户一条、O(1) 存储，而且改密踢全部设备这个刚需黑名单做不到，所以选它。

#### ⚠️ 卡壳点

宽限的因果链必须说全：**iat 秒级 vs revoke_before 毫秒级 → 同秒新 token iat ≤ 登出毫秒 → 严格小于判断误杀**；TTL 是"token 寿命+60s"不是固定值；找回密码也写 revoke_before 的理由（被盗号改密场景）是加分项。

### 18. 登录风控 Redis + 本地内存双保险（原 Q26 · 🟠P1）

#### ① 标准参考答案（基于真实代码）

参数（`LoginRiskControlServiceImpl`，全部可配）：`maxFailures=5` 次失败触发锁定、锁定 `lockDurationSeconds=900`（15 分钟）、计数窗口 `counterTtlSeconds=1800`（30 分钟）、总开关 `login-risk-control-enabled`。

**Redis 主路径**：登录失败 `recordFailure` → `INCR auth:login:fail:count:{username}` 并 `EXPIRE 1800s` → 计数到 5 → `SET auth:login:fail:lock:{username} = lockedUntil 毫秒`（TTL 900s）。每次登录前 `assertLoginAllowed` 读锁 key，未到解锁时间 → `BusinessException(429, "剩余 N 秒后重试")`，经全局异常处理器返回 `Result{code:429}`。登录成功 `clearFailures` 删计数和锁两个 key。

**双保险机制，两道防线**：

1. **装配期可选**：构造器注入的是 `ObjectProvider<StringRedisTemplate>`，`getIfAvailable()` 在项目根本没配置 Redis 时（Spring Boot 不注册该 Bean）返回 null 而不是启动失败——风控服务在无 Redis 环境照样能起；
2. **运行期降级**：所有 Redis 操作包 `try-catch(Exception)`，Redis 宕机/超时 → 自动落到三张 `ConcurrentHashMap`（失败计数 / 计数过期时间 / 锁定截止时间），逻辑与 Redis 路径同构。

所以 **Redis 挂了风控还能用**，只是保护强度从"全局 5 次"弱化为"单实例 5 次"（本地 Map 多实例间不共享，阈值变相放大 N 倍），且恢复后本地状态不回灌 Redis——是可用性优先的尽力而为，不是强一致。

**本地内存的治理（修复 #7）**：`cleanupLocalState` 只清"当次访问到的用户名"，Redis 宕机期间若遭遇**随机用户名攻击**，没再被访问的陈旧条目会滞留导致内存缓慢增长 → `@Scheduled` 每 10 分钟（600000ms）全量清理过期项兜底；Redis 正常时这些 Map 本来就是空的，这个定时任务零成本。

#### ② 预埋追问逐条拆解

**追问①：Redis 挂了风控还能用吗？**
能。两层保障：没配 Redis（Bean 不存在）→ `ObjectProvider.getIfAvailable()` 返回 null 直接走本地；配了但运行期挂 → try-catch 降级本地。但要诚实说出代价：多实例下每台各自计数，"5 次锁定"实际变成"每实例 5 次"，爆破者换节点还能多试；且降级期间的锁定状态其它实例看不到。单实例部署（本项目现状）下这些差距都不存在。

**追问②：ObjectProvider.getIfAvailable 是什么？**
Spring 的**可选依赖**注入接口：普通 `@RequiredArgsConstructor` 注入 `StringRedisTemplate` 时 Bean 不存在会直接启动报错；`ObjectProvider<T>` 把解析推迟到 `getIfAvailable()` 调用时，不存在给 null，存在给实例。适合"有它更好、没它也能活"的增强型依赖——和 `@Autowired(required=false)` 目标一样，但类型安全、不依赖字段注入。项目里两处用了它：这里的风控和 Outbox 的 `NotificationEventPublisherImpl`（RabbitTemplate），是同一个设计语言：**辅助能力不许变成启动硬依赖**。

**追问③：双保险的一致性？**
不是强一致，是**可用性优先的尽力而为**：本地状态不回灌 Redis、跨实例不可见、两套实现可能有细微行为差异。取舍逻辑：风控是安全增强层，它自己故障时不能反过来阻断所有用户登录（那等于 Redis 变成登录的单点）；弱化保护好过功能整体消失。如果要多实例强一致，就把本地兜底改成"Redis 挂时直接 fail-open 只记日志告警"或引入共享存储——按业务风险选。

**追问④：锁定 15 分钟合理吗？**
从暴力破解看：15 分钟 / 5 次 ≈ 每小时每账号最多 20 次尝试，字典攻击速率被压到基本不可行；对正常用户，误锁 15 分钟可接受（还能走找回密码）。可改进方向主动说：a) **渐进惩罚**（第一次锁 5 分钟、翻倍递增，比一刀切 15 分钟对用户更友好、对攻击者更狠）；b) 锁定前先上**验证码**（人机分离，避免误伤真实用户）；c) 叠加 **IP 维度**计数（当前按用户名，攻击者换用户名横向撞库不受单账号锁限制）；d) 锁定事件通知用户/管理员。

#### 🎤 面试版总结

> 登录风控是五次失败锁十五分钟、计数窗口三十分钟，正常流程全走 Redis：INCR 计数、到阈值写一个带 TTL 的锁 key，登录前先查锁，没到点就抛 429 提示剩余秒数。双保险是两道防线：装配期用 ObjectProvider 注入 StringRedisTemplate，项目没配 Redis 时 getIfAvailable 拿到 null，服务照样启动；运行期 Redis 挂了，所有操作 try-catch 降级到三张 ConcurrentHashMap，逻辑同构。所以 Redis 挂了风控还能用，代价是多实例下本地计数不共享、保护从全局五次弱化成单实例五次，这是可用性优先的取舍——安全增强层不能反过来变成登录的单点。另外本地兜底配了每十分钟的全量过期清理，防随机用户名攻击把内存慢慢撑大。

#### ⚠️ 卡壳点

数字链 **5 次 / 900s 锁 / 1800s 计数窗口 / 10min 本地清理**；双保险是**两道**（装配期 ObjectProvider + 运行期 try-catch），只说一道会丢分；诚实认"单实例弱化、不回灌"再给取舍理由；ObjectProvider 对比 `@Autowired(required=false)` 是追问②的加分点。

### 19. 用户信息缓存角色变更时为什么要主动清（原 Q28 · 🟠P1）

#### ① 标准参考答案（基于真实代码）

**缓存本体**：`JwtAuthenticationFilter` 鉴权时每个请求读 `user:info:{userId}`，值是 `"status:role"` 两个 Short 拼串，**TTL 5 分钟**（`USER_CACHE_TTL_MINUTES = 5L`）；未命中查 `userRepository.findById` 回填。存在的原因：JWT 无状态，每个请求都要拿用户的 status（禁用判断）和 role（授权），不缓存就是每请求一次 DB 读。

**为什么必须主动清**：缓存里存的是**权限语义数据**。变更点不清 = 越权窗口 = 缓存剩余 TTL（最长 5 分钟）：

- **降权/禁用方向最危险**：管理员被降为 USER、账号被禁用 → Redis 里旧 `role=ADMIN / status=ACTIVE` 还能用最长 5 分钟 → **已被处置的账号继续行使管理权限**；
- 提权方向：普通用户升管理员 5 分钟不生效（体验问题，非安全问题）。

**清理点全景（代码闭环）**，模式统一为 **cache-aside + 先写库后删缓存**：

| 变更点 | 动作 |
| --- | --- |
| `AdminUserServiceImpl.updateUserRole` | `invalidateUserInfoCache`（删 `user:info:`） |
| `AdminUserServiceImpl.updateUserStatus` | 清缓存；**禁用时再 `forceInvalidateUserTokens`** |
| `forceInvalidateUserTokens`（禁用/重置密码） | 写 `jwt:revoke_before`（TTL=token 寿命+60s）**强制所有旧 token 立即下线** + 删缓存 |
| `UserProfileServiceImpl.changePassword` / `AuthServiceImpl.logout/resetPassword` | 写 revoke_before + 删缓存 |

禁用是"清缓存 + 吊销 token"双动作：清缓存只影响后续请求的鉴权数据加载，**已签发的 JWT 本身仍有效**，所以必须叠加 revoke_before 才能做到"禁用即下线"。

#### ② 预埋追问逐条拆解

- **① 不清会怎样？** 5 分钟越权窗口，重点讲**降权/禁用方向**（提权只是体验问题）。禁用场景项目做了双动作（清缓存 + revoke_before 吊销全部 token），可主动展开当加分项。
- **② 为什么不直接缩短 TTL？** 治标不治本：缩到 10s 仍有 10s 窗口，问题没有消失；且 TTL 越短命中率越低，每次未命中就是一次 DB `findById`，用户表读压力全回来。窗口的正解是**事件驱动的主动失效**（变更时刻删），TTL 只该做兜底不该做一致性主力。
- **③ 主动清 + TTL 是双保险吗？** 是分层不是冗余：主动清管"变更即时生效"（一致性主力）；TTL=5min 管"兜底自愈"——删缓存失败、漏清、极端不一致时最多 5 分钟自动收敛，同时保证缓存条目最终回收。
- **（加分）为什么只缓存 status:role 不缓存整个 User？** 只缓存鉴权决策必需的两个字段，失效点明确可控（角色/状态变更处）；缓存整对象则昵称、头像任何字段变更都得清，失效点爆炸。

#### 🎤 面试版总结

> JWT 无状态，每个请求都要加载用户的 status 做禁用判断、role 做授权，所以我在 Redis 缓一个 "status:role" 拼串、五分钟 TTL，把每请求一次的数据库读挡掉。但缓存的是权限语义数据：管理员降权、账号禁用如果不主动清，被处置的账号还能拿着旧权限再用最长五分钟，这是越权窗口。所以所有变更点都是先写库后删缓存——改角色清缓存；禁用账号除了清缓存还写 revoke_before 把该用户所有旧 token 立即吊销强制下线，因为清缓存只管后续请求，已签发的 JWT 本身还有效。主动清管即时生效，TTL 五分钟只做兜底自愈，两层是分工不是冗余。至于缩短 TTL：窗口只是变小没有消失，命中率还掉，未命中就是每请求查一次库，读压力全回来了。

#### ⚠️ 卡壳点

窗口重点讲**降权/禁用方向**（提权是体验问题）；禁用 = 清缓存 + revoke_before **双动作**（理由：清缓存不影响已签发 JWT）；"先写库后删缓存"顺序；TTL 是兜底不是一致性主力。

### 20. Flyway 的 V1 为什么是空 baseline？双轨制是什么（原 Q11 · ⚪P2 ⭐）

#### ① 标准参考答案（基于真实代码）

**目录三件套**：`db/migration/`（唯一增量结构变更入口）；`db/legacy/`（历史手工脚本归档，仅审计留档、不再执行）；`db/init/`（docker 首次初始化：PostGIS/pgvector 扩展 + assistant_cache 表）。

**V1 为什么空**：`V1__baseline.sql` 内容就一行 `SELECT 1;`。项目是**既有库中途引入 Flyway**——表结构由 `ddl-auto=update` 时期 + 手工脚本演进而来，无法安全重放。配置 `spring.flyway.baseline-on-migrate=true` + `baseline-version=0`：既有库首次带 Flyway 启动自动打 version=0 基线**认领现状**（不重放历史），V1 仅作版本链起点标记，自此所有变更新增 `V{n}__描述.sql`。

**双轨制**：**建表**归 Hibernate——`DDL_AUTO=update` 仅全新库首次启动用，之后（生产默认）`validate` 只校验不改表，**建表的单一真相源是 JPA 实体**；**结构变更**归 Flyway——V{n} 增量脚本，版本化、可审计、checksum 校验，版本号只增不改（写错追加新版本订正）。

**为什么不写全量 `V2__init.sql` 实现"纯 Flyway"**（README 三条权衡）：

1. **一致性风险**：30+ 实体的手写 DDL 必须与 Hibernate `validate` 完全一致，任何字段类型/精度/索引偏差都让 validate 失败或数据错位；
2. **既有库冲突**：既有库已有表，全量脚本必须 `CREATE TABLE IF NOT EXISTS`，而它会**把真实结构差异静默吞掉**（库被手工改过，差异不报错，直到 validate 或运行时才炸，极难定位）；
3. **双份真相源**：实体和手写 DDL 两份 schema 定义，改实体必须同步改脚本，必然漂移。

这是"存量库引入版本化迁移"的**工程妥协而非 Flyway 教科书用法**，但当前阶段收益/风险比最高。

#### ② 预埋追问逐条拆解

- **① 为什么不写全量 V2__init.sql？** 上面三条权衡说全，落点在"双份真相源必然漂移"。
- **② IF NOT EXISTS 会掩盖什么？** 掩盖"既有库真实结构与脚本假设不一致"：表被手工改过时 `IF NOT EXISTS` 直接跳过建表，差异不暴露，脚本是否真的描述了库变得不可知——问题延迟到 validate/运行时爆炸。
- **③ 全新库怎么搭建？** docker 起 PG（`db/init` 卷装扩展+assistant_cache）→ 首次启动 `DDL_AUTO=update` 让 Hibernate 建全量表 → 改回 `validate` → 之后一律走 V{n}（README 规则 4）。本地实验库可 `FLYWAY_ENABLED=false` 跳过。
- **④ 双份真相源指什么？** "实体定义的 schema" 与 "手写全量 DDL 的 schema" 两份并行真相；双轨制把它收敛为"建表真相只有实体一份，Flyway 只记增量"，从根上消漂移。（加分）未来纯 Flyway 化路线：干净库 `ddl-auto=create` → `pg_dump --schema-only` 导出 → 整理成 `V{n}__init.sql` → CI 空库验证 validate 通过。

#### 🎤 面试版总结

> 项目是在既有库上中途引入 Flyway 的，表结构是 Hibernate update 时期加手工脚本演进的，没法安全重放，所以用 baseline-on-migrate 打 version=0 基线认领现状，V1 就一行 SELECT 1 当版本链起点。之后是双轨制：建表的单一真相源是 JPA 实体，全新库首次 DDL_AUTO=update 建表、生产永远 validate 只校验；结构变更一律走 V{n} 增量脚本，版本号只增不改，靠 checksum 保证。当时权衡过写全量 init 脚本做纯 Flyway，放弃了：三十多个实体的手写 DDL 要跟 validate 完全对齐太难；既有库跑全量脚本必须 IF NOT EXISTS，会把真实结构差异静默吞掉；而且实体和 DDL 两份真相必然漂移。这是存量库引入版本化迁移的工程妥协，不是教科书用法，但当下收益风险比最高。

#### ⚠️ 卡壳点

V1 内容就一行 **SELECT 1**；`baseline-on-migrate=true + baseline-version=0`；三条权衡说全（尤其 **IF NOT EXISTS 吞差异**）；主动认"工程妥协非教科书用法"；建表真相源 = 实体（不是脚本）。

### 21. traceId 怎么全链路串联的（原 Q30 · ⚪P2）

#### ① 标准参考答案（基于真实代码）

**三件套**：`RequestTraceFilter`（@Component servlet filter，位于 Spring Security 链之后、DispatcherServlet 之前——业务层日志都能拿到）+ `RequestTraceContext` 工具类 + 日志 pattern。

**流程**：请求进入 `resolveTraceId`——**优先沿用外部 `X-Trace-Id` 请求头**（跨系统透传的口子），其次 request attribute（同请求内复用），否则 `UUID.randomUUID()` 去横线生成 32 位 hex。写入三个落点：

1. request attribute（同请求内任何代码可取）；
2. **响应头 `X-Trace-Id`**（前端/运维拿到可反馈排查）；
3. **MDC.put("traceId")**。

`finally` 里 `MDC.remove`——Tomcat 线程池复用线程，不清会把上一请求的 traceId 串到下一请求（**串号**）。

**日志**：`logging.pattern.console` 配 `[%X{traceId:-}]`（黄色高亮），`%X` 从 MDC 取，`:-` 是取不到给默认空串。

**审计串联**：`OperationLogAspect` 用 `RequestTraceContext.getCurrentTraceId()`（先查 MDC、fallback `RequestContextHolder` 的 request attribute），落 `AdminOperationLog.traceId` 列（截 40 字符）→ 后台系统日志页与服务器日志按同一 traceId 关联。

**诚实局限（项目真实存在）**：MDC 是 ThreadLocal，异步/池化线程不继承——`EmailService.sendHtml` 是 `@Async`（线程池线程日志无 traceId），`@RabbitListener` 消费线程、`@Scheduled` 调度线程同样没有。当前接受此局限；要修用 `TaskDecorator`（任务提交时拷贝 MDC contextMap、执行时回填）。

#### ② 预埋追问逐条拆解

- **① MDC 是什么？** slf4j 的 Mapped Diagnostic Context，底层是 **ThreadLocal 的 Map**，日志 pattern `%X{key}` 输出；作用是把请求级上下文带进每条日志而不改方法签名。
- **② 异步线程会丢吗？** 会——MDC 基于 ThreadLocal；`InheritableThreadLocal` 只在子线程**创建时**复制父线程值，线程池线程是**复用**的不触发复制。项目真实例子：邮件 @Async。解法：TaskDecorator 或显式传参。
- **③ 跨服务呢？** 当前单体无跨服务链路，但 `X-Trace-Id` 请求头已预留透传口（上游带头即沿用）。演进微服务用 **Micrometer Tracing**（Sleuth 在 Boot 3 后停更并入）——W3C traceparent 标准头透传 + span 语义。
- **④ 日志 pattern 怎么配？** `[%X{traceId:-}]`——`%X` 取 MDC、`:-` 默认值语法（无 traceId 留空，避免异步线程日志打 null）。

#### 🎤 面试版总结

> 一个 servlet Filter 在 Security 链之后、DispatcherServlet 之前拦每个请求：优先沿用外部传来的 X-Trace-Id 头，没有就 UUID 生成 32 位，写三个地方——请求 attribute、响应头 X-Trace-Id、还有 MDC。日志 pattern 配 %X{traceId}，MDC 底层是 ThreadLocal 的 Map，同请求内所有业务日志自动带上；请求结束 finally 里 MDC.remove，防 Tomcat 线程复用把 traceId 串号到下一个请求。审计切面取同一个 traceId 落到操作日志表的列里，后台审计记录和服务器日志能按它关联。诚实说局限：MDC 是线程级的，邮件 @Async、MQ 消费线程、定时调度这些池化线程拿不到，要修得用 TaskDecorator 在任务提交时拷贝 MDC。

#### ⚠️ 卡壳点

三落点（attribute / **响应头 X-Trace-Id** / MDC）+ 生成优先级（头 > attribute > UUID）；**finally remove 防串号**；主动认 @Async/MQ/调度线程没 traceId（真实例子：EmailService）；跨服务答 **Micrometer Tracing**（不是 Sleuth）。

### 22. actuator 端口怎么收窄的？SB4 包迁移踩过坑吗（原 Q32 · 🟠P1 ⭐）

#### ① 标准参考答案（基于真实代码）

**收窄方案**：`management.server.port=9091` **独立 management 端口**——actuator 整体搬离主端口，**8080 上根本不存在 /actuator 路径**（最小暴露面：公网扫描不到路径存在性）；只暴露 `health,info,prometheus,metrics` 四端点 + `management.endpoint.prometheus.enabled=true`（SB4 + micrometer 2.x 下 registry 由 classpath 自动激活，无需配置）。部署层：docker 编排 **9091 不映射宿主机**、生产绑内网/localhost，仅 Prometheus 与 healthcheck 访问；`ops/prometheus.yml` target `backend:9091`（容器网络内），15s 抓取间隔。

**为什么独立端口而非另外两个**：

- `hasIpAddress`：仍在主端口，暴露面没变，只是应用层来源校验；路径存在性可被扫描；代理/容器网络下 IP 白名单难维护；
- Basic Auth：同样主端口暴露，凭据要写进 Prometheus 抓取配置，多一套凭据管理，泄露即全量指标暴露；
- **独立端口 = 网络层隔离**："默认不该被公网访问的东西就不监听公网"，配合不映射/防火墙是纵深防御，也无需给 actuator 单做认证链。

**SB4 踩坑①（MeterRegistryCustomizer 包迁移）**：从 `org.springframework.boot.actuate.autoconfigure.metrics` 迁到 `org.springframework.boot.micrometer.metrics.autoconfigure`（新模块 spring-boot-micrometer-metrics）。升级时 **import 直接编译不过**——好在是显式失败不是静默。它的作用：给所有指标注入 `application/module=discover` 通用标签，Grafana 按应用维度聚合。

**SB4 踩坑②（EnvironmentPostProcessor 接口 FQN 迁移）**：接口从 `org.springframework.boot.env.EnvironmentPostProcessor` 移到 `org.springframework.boot`（旧路径仅 deprecated 桥接），**spring.factories 的注册 key 必须同步写新 FQN** `org.springframework.boot.EnvironmentPostProcessor`——否则 processor 不被发现、**静默失效**：AI 助手关闭时的自动配置排除不生效，空 api-key 启动报错直接回归。注意与 AutoConfiguration 不同：EPP 的发现走 spring.factories、不走 .imports。

#### ② 预埋追问逐条拆解

- **① 独立端口 vs hasIpAddress vs Basic Auth？** 核心句"**网络层隔离 vs 应用层校验**"——前两种暴露面不变，只是加门禁；独立端口从根上不监听公网，纵深防御。
- **② MeterRegistryCustomizer 包迁移？** 新包 + 新模块 spring-boot-micrometer-metrics；编译期显式暴露（import 报错），危害低但必须知道去哪找新包。
- **③ EnvironmentPostProcessor 注册 key 变化？** key 必须用新 FQN（接口包从 .env 挪到根包）；风险是**静默失效**（不报错但 processor 没跑，autoconfigure 排除失灵）；与 autoconfigure 的 .imports 发现机制区分开。
- **④ Prometheus 怎么抓 management 端口？** `ops/prometheus.yml`：job=smart-campus-backend，`metrics_path=/actuator/prometheus`，target=`backend:9091`（docker 网络名:管理端口），15s 间隔；compose 里 9091 不映射宿主机。

#### 🎤 面试版总结

> actuator 整体隔离到独立 management 端口 9091，主端口 8080 上根本不存在 /actuator 路径，只暴露 health、info、prometheus、metrics 四个端点；docker 里 9091 不映射宿主机、生产绑内网，Prometheus 在容器网络里直接抓 backend:9091。没用 hasIpAddress 或 Basic Auth，因为那两种只是应用层校验、暴露面没变；独立端口是网络层隔离——不该公网访问的东西就不监听公网。SB4 升级踩了两个包迁移坑：MeterRegistryCustomizer 挪到 spring-boot-micrometer-metrics 新模块，这个编译期就暴露；更隐蔽的是 EnvironmentPostProcessor 接口换了 FQN，spring.factories 注册 key 不跟着改的话 processor 静默失效，AI 助手关闭时的自动配置排除直接失灵，空 api-key 启动报错就回归了。

#### ⚠️ 卡壳点

端口数字 **9091 / 8080**、四端点清单；核心句"**网络层隔离 vs 应用层校验**"；两个坑分清——**MeterRegistryCustomizer 显式编译失败 / EPP 注册 key 静默失效**；EPP 走 spring.factories 不走 .imports。

### 23. 审计落库为什么用 REQUIRES_NEW（原 Q34 · ⚪P2）

#### ① 标准参考答案（基于真实代码）

**场景**：`@OperationLog` 注解打在 **Service 层方法**上（AdminContentServiceImpl 删分享/删回复、举报、打卡、发分享/回复等），这些方法多自带 `@Transactional`。`OperationLogAspect` @Around 包住业务方法，**finally 里**调 12 参数 `record` 落审计（成功失败都记，`operationStatus` 1/0 区分，失败把异常信息拼进 summary 截 300）。

**双入口设计**：6 参数 `record` 用默认 REQUIRED（26 处旧手动调用点向后兼容）；12 参数 `record`（AOP 专用）标 `@Transactional(propagation = Propagation.REQUIRES_NEW)`。

**为什么 REQUIRES_NEW**：失败审计必须独立于主业务事务存活。业务抛异常时，切面 finally 执行的时点上，主事务**要么已回滚**（审计切面在事务边界外层）**要么挂着 rollback-only**（审计切面被事务切面包在里层）——后者情形 REQUIRED 会加入 rollback-only 事务，提交时抛 `UnexpectedRollbackException`，**失败记录跟着一起丢**；REQUIRES_NEW 挂起外层、开新连接独立提交，**两种切面顺序下都确定性落库**，不依赖顺序假设。

**反方向保护**：审计落库自身失败（DB 抖动）只 `log.warn` 不抛——审计是治理辅助，不能反噬主业务可用性。

**代价（主动说）**：REQUIRES_NEW 占**第二个数据库连接**（外层挂起不释放 + 新事务再取一个），高峰期连接池压力；同线程两个事务**竞争同一行锁会自锁**——审计只 INSERT 独立新行、不碰业务表，天然规避。所以 REQUIRES_NEW 不能滥用，只给"必须独立提交"的旁路动作。

**语义辨析**：主业务回滚了、成功审计还在——审计记录的是"**操作尝试**"不是"业务结果"，`operationStatus=0` + 异常信息本身就是治理要抓的对象，宁可多记不可漏记；成功审计先提交、主业务之后回滚的极端窗口确实可能错位，治理场景可接受。

#### ② 预埋追问逐条拆解

- **① 不用 REQUIRES_NEW 会怎样？** 失败记录被主业务回滚连带丢失（rollback-only 下 REQUIRED 提交抛 UnexpectedRollbackException）——**而失败操作恰恰最需要审计**。切面与事务切面的相对顺序不同，表现不同；REQUIRES_NEW 对两种顺序都稳。
- **② REQUIRES_NEW 的代价？** 第二个连接/连接池高峰压力；外层与新事务同行锁竞争会**自锁死锁**（本项目规避：审计只 INSERT 新行）；两个事务上下文的调试复杂度。
- **③ 主业务回滚了审计还在，算问题吗？** 明确设计为记录"尝试"：operationStatus 区分成败、失败拼异常信息——失败本身就是审计对象，治理取向是宁可多记不可漏记。
- **④ 审计漏了怎么办？** 切面 catch 只 warn（可用性优先）；影响=该条操作无审计行；兜底是 26 处手动 record 入口仍在 + warn 日志可接告警；要更稳可做本地队列异步补偿，当前选择简单可靠。
- **（加分，与 #15 成对）** Q22 是"批量调度故意**不加**事务"（失败单元=单条事件），Q34 是"审计**必须独立**事务"（失败单元=审计自身）——**事务边界按失败单元语义设计**，不是事务越多越安全。

#### 🎤 面试版总结

> 操作审计注解打在 Service 方法上，切面 finally 里落库，业务成功失败都要记。落库方法标 REQUIRES_NEW 独立事务：业务抛异常时主事务要么已回滚、要么挂着 rollback-only，如果审计用默认 REQUIRED 加进去，提交时直接 UnexpectedRollbackException，失败记录跟着丢——而失败操作恰恰最该被审计。REQUIRES_NEW 挂起外层、开新连接独立提交，无论审计切面和事务切面谁包谁都确定性落库。反方向审计自己失败只 warn 不抛，治理辅助不能反噬业务。代价主动认：占第二个连接、高峰有连接池压力，同线程两事务抢同一行锁会自锁——审计只 INSERT 新行规避了，所以这个传播级别不能滥用。语义上审计记的是"操作尝试"，失败本身就是治理对象，宁可多记不可漏记。

#### ⚠️ 卡壳点

注解在 **Service 层**（不是 Controller）；REQUIRED 的死因 = 加入 rollback-only 事务提交爆 **UnexpectedRollbackException**；代价主动认（**第二连接 + 行锁自锁**与规避方式：只 INSERT）；与 #15 成对讲——**失败单元决定事务边界**。

### 24. GitHub Actions 部署链路（原 Q36 · ⚪P2）

#### ① 标准参考答案（基于真实代码）

单 workflow `.github/workflows/deploy.yml`（名 `Deploy Place Explore`），触发 `on: push: branches: [main]`，单 job `build-and-deploy`（ubuntu-latest），推 main 即全自动构建+部署。步骤链（代码实证）：

| 阶段 | 步骤 | 关键细节 |
|---|---|---|
| 后端构建 | `checkout@v4` → `setup-java@v4` → `mvn -B package` | JDK 21 temurin，`cache: maven` 缓存依赖；working-directory `smart-campus-backend`；pom 未配 skipTests → **package 默认生命周期先跑单测再打包**，测试挂则部署中断 |
| 定位产物 | find jar → `GITHUB_OUTPUT` | `find target -maxdepth 1 -name "*.jar"` 排除 `*sources*`/`*javadoc*`，取第一个，输出 `jar_path` 供后续步骤引用 |
| 前端构建 | `setup-node@v4` → `npm ci && npm run build` | Node 20，npm cache 以 package-lock.json 为 key；env 注入 `VITE_AMAP_JS_KEY`/`VITE_AMAP_SECURITY_JS_CODE`（**高德 key 构建期烙进 dist**） |
| 传输 | `ssh-action@v1.0.3` + `scp-action@v0.1.7` ×3 | 先 SCP 同步仓库 `deploy/*` 到 VPS `/opt/place-explore/deploy`（strip_components: 1，**脚本唯一真源在仓库**，2026-08-29 事故后新增）；再 SSH 清建远端临时目录 `/tmp/deploy-incoming`；SCP 传 jar 与 `dist/*`，均 `strip_components: 2` 剥掉仓库相对路径 |
| 部署 | `ssh-action` 执行 | `set -e`（任一命令失败即中止）→ find jar → `bash /opt/place-explore/deploy/deploy-backend.sh "$JAR_FILE"` → `deploy-frontend.sh /tmp/deploy-incoming/dist` → 清理临时目录 |

Secrets 全套：`VPS_HOST`/`VPS_USER`/`VPS_SSH_KEY`/`VITE_AMAP_JS_KEY`/`VITE_AMAP_SECURITY_JS_CODE`——主机、账号、私钥、高德 key 全走 GitHub Secrets，不落仓库。CI 只负责"构建+传输+调用脚本"，**版本化/切链/回滚逻辑在服务器端脚本**（职责分离，脚本可独立手执行）。

#### ② 预埋追问逐条拆解

1. **构建 jar + dist 怎么做？** 后端 `mvn -B package` 出 Spring Boot fat jar（repackage），find 定位排除 sources/javadoc 二次产物；前端 `npm ci`（严格按 lock 装）+ vite build 出 dist；高德 key 经 env 构建期注入（Vite 静态替换 `import.meta.env`）。
2. **SCP + SSH 的安全？** 三层：①认证走 SSH 私钥（secrets.VPS_SSH_KEY），无密码明文；②所有敏感值（host/user/key/高德 key）存 GitHub Secrets，日志自动打码；③传输目标是 `/tmp` 临时目录，由服务端部署脚本校验接管后才落正式目录，CI 不直接碰运行目录。
3. **CI 失败怎么发现？** ①任一步骤非零退出整个 job 红（含远端 `set -e` + 部署脚本健康检查失败 exit 1 会经 ssh-action 回传）；②GitHub Actions 默认对失败 run 发邮件/可配 webhook；③构建失败时根本走不到 SCP——**不会部署半成品**。
4. **为什么不用 Jenkins/ArgoCD？** Jenkins 要自维护实例和插件，单人项目用托管 Actions 零运维、与 push 事件原生集成；ArgoCD 是 k8s GitOps 体系，本项目生产形态是 **systemd + nginx 单机**，引 k8s 属过度设计。选型逻辑：**工具与部署形态匹配**，不是越重越好。

#### 🎤 面试版总结

"我是一条 GitHub Actions workflow，push main 触发：先 JDK21 下 mvn package 打后端 fat jar——因为没配 skipTests，**打包前会先跑单测，测试不过部署直接中断**；再 Node20 下 npm ci 加 vite build，高德 key 从 Secrets 构建期注入。然后 SCP 把 jar 和 dist 传到服务器临时目录，最后 SSH 调服务器上的部署脚本完成发布、清理临时目录。主机、SSH 私钥、高德 key 全部走 GitHub Secrets 不落仓库。CI 只管构建和传输，版本化、软链切换、回滚都在服务器端脚本里，可以脱离 CI 手动执行——职责是分开的。没选 Jenkins/ArgoCD 是因为生产就是 systemd 单机，Actions 托管免运维，和部署形态匹配。"

#### ⚠️ 卡壳点

链路顺序背熟（checkout→JDK21→package 含单测→find jar→Node20→npm ci+build 注入高德 key→SSH 备临时目录→SCP×2 strip_components:2→SSH 跑脚本）；亮点句"**package 默认先跑单测，测试挂就不部署**"；追问④落点"**工具与部署形态匹配**"不是嫌重。

### 25. 版本化发布 + 软链接 + 一键回滚（原 Q37 · ⚪P2）

#### ① 标准参考答案（基于真实代码）

三个脚本（deploy/ 目录，代码实证）：

**deploy-backend.sh**（`set -euo pipefail`）：
- 版本化：拷贝传入 jar 为 `releases/{原文件名}-{时间戳}.jar`（RELEASE_DIR=`/opt/place-explore/backend/releases`）
- 固定入口：`app.jar` 软链（`/opt/place-explore/backend/app.jar`），`ln -sfn` **原子切换**指向新版本——systemd 配置永远只认 `app.jar` 这一个路径；切链**前**记录 `PREV_JAR`（当前软链指向，即回滚目标）
- 重启+健康检查（2026-08-29 事故后升级）：`systemctl restart` → 轮询 `curl -fsS http://localhost:9091/actuator/health`（management 端口只绑 localhost，最长 **90s**、每 3s 一次，循环内同时查 `is-active`——进程崩了立即失败不等超时）
- **失败自动回滚**：健康检查不过 → `fail_and_rollback`：软链切回 `PREV_JAR` + restart + 回滚后再做一轮健康确认（仍不过则报"请立即人工介入"）→ exit 1 让 CI 感知。动机：事故当晚服务 `is-active` 但接口全 500，**进程存活 ≠ 业务健康**，带病启动被静默放行
- 清理：KEEP_RELEASES=**5**，`ls -t | tail -n +6 | xargs -r rm -f` 只留最新 5 版

**deploy-frontend.sh**：同款套路——`/var/www/place-explore/releases/{时间戳}/` 目录 + `current` 软链 `ln -sfn`，保留 5 版，顺手清理历史 zip。

**rollback.sh**：三个子命令——`list`（列历史版本）/ `backend <jar名>`（`ln -sfn` 切回 + restart）/ `frontend <目录名>`（**仅切链，不重启**——nginx 静态托管，切完即生效）。

回滚速度：**一次软链切换 + 一次 restart，秒级**；前端更快，只切链。

#### ② 预埋追问逐条拆解

1. **软链接 current → release 的好处？** ①发布 = 拷新版本 + 一次 `ln -sfn`，symlink 替换是原子操作，不存在"原地覆盖运行中文件"的半写状态；②systemd/nginx 永远只引用固定路径（app.jar/current），配置零改动；③历史版本留 5 份，回滚有物料；④版本目录带时间戳，可追溯哪次发布。
2. **回滚多快？** 后端 = 切链 + restart（systemd 拉起 JVM，秒级到十几秒）；前端 = 仅切链，nginx 下个请求就 serve 旧目录，近乎即时。对比"重新跑 CI 回滚到旧 commit"要等整个构建链，分钟级。
3. **回滚数据库怎么办？（难）** 主动认：**Flyway 迁移不可逆**（没有 down migration），本方案只回滚代码不回滚库。所以迁移设计上要求**向后兼容**（先加列后删列的两段式、新代码兼容旧 schema），让"旧代码 + 新 schema"能跑——回滚安全的前提是迁移不 breaking。这是该方案的明确边界。
4. **蓝绿/金丝雀做过吗？** 没做。单机 systemd 形态做不了真蓝绿（需要双实例 + 流量切换层）；要上蓝绿得升双机 + LB 或 k8s。当前量级收益不抵复杂度，但**路径是清楚的**：软链版本化已经是蓝绿的雏形（多版本并存，缺的是流量按比例切）。

#### 🎤 面试版总结

"发布脚本做了版本化：每次部署把 jar 拷成带时间戳的版本放进 releases 目录，再 `ln -sfn` 把固定的 app.jar 软链原子切到新版本，systemd 只认这个固定路径，切链前先记下旧版本当回滚目标。切完 restart，然后轮询 actuator health——最长等 90 秒，进程崩了立即失败；健康检查不过就**自动把软链切回上一版重启**，回滚后还做一轮健康确认，再不行就报人工介入，最后 exit 1 让 CI 变红。这套升级来自一次真实事故：服务进程是 active 的但接口全 500，进程存活不等于业务健康。前端同款：时间戳目录 + current 软链。手工回滚脚本一条命令：后端切链加 restart，前端只切链不重启，因为 nginx 是静态托管——秒级完成。数据库是这套方案的边界：Flyway 迁移不可逆，所以迁移都设计成向后兼容，回滚只回代码。蓝绿金丝雀没做，单机 systemd 做不了真蓝绿，但软链版本化本身就是蓝绿的雏形，缺的只是流量切换层。"

#### ⚠️ 卡壳点

数字链 **ln -sfn / 切链前记 PREV_JAR / 保留 5 版 / health 轮询 90s + 失败自动回滚**；升级动机一句"**进程存活 ≠ 业务健康**"；前端回滚**只切链不重启**（nginx 静态）；追问③主动认"**迁移不可逆 → 迁移设计向后兼容，回滚只回代码**"；追问④"软链版本化是蓝绿雏形"体现认知而非心虚。

### 26. Pinia + 高德地图怎么集成（原 Q41 · ⚪P2）

#### ① 标准参考答案（基于真实代码）

**Pinia 三个 store（全部 setup 语法 `defineStore(id, () => {...})`）**：

| Store | 职责 | 关键实现 |
|---|---|---|
| `user.js` | 会话与身份 | token+userInfo（localStorage 持久化，初始化时 token 解析兜底）；computed 派生 `isLoggedIn`/`isAdmin`/`isSuperAdmin`/`isAdminOrAbove`（角色常量）；login 后 `syncCurrentUser` 拉全量档案；logout **先调后端吊销 JWT（revoke_before），失败也不阻塞本地清理** |
| `poi.js` | POI 数据列表 | **双列表** `mapPoiList`（视口 bounds 拉取）/`searchPoiList`（搜索结果）+ `activeSource` 派生 `visiblePoiList`；**`shallowRef` 存大数组**避免深层响应式开销；`poiEntityCache`（Map）实体缓存 `getCachedPOIById`；`boundsSummary` 记 total/limit/truncated 截断提示；`fetchInBounds` 默认 **limit=1200** |
| `map.js` | 地图与路线状态机 | center/zoom（默认中国中心 35.8617,104.1954 zoom 5）；路线规划全套状态（routeStart/End/中间点/拾取模式 routePickMode/推荐路线 activeRecommendedRoute）；`planRouteAsync` **多点时逐段调规划 API 再 `mergeRoutePlans` 合并**（去重点位、累加距离时长、步骤指令拼接）；`selectPOI` 联动 `flyTo` |

**高德集成（utils/amap.js + MapContainer.vue）**：
- **加载时机**：不进 index.html，**按需动态加载** `loadAmapSDK()`——单例 Promise（`amapLoaderPromise` 防重复）、先查 `window.AMap`、动态插 `<script src="https://webapi.amap.com/maps?v=2.0&key=...">`（async+defer+`data-amap-sdk` 标记查重，幂等），失败 reject 明确报错。
- **key 管理**：`VITE_AMAP_JS_KEY`/`VITE_AMAP_SECURITY_JS_CODE` 走 `.env` → CI 从 **GitHub Secrets 构建期注入**；securityJsCode 挂 `window._AMapSecurityConfig`；缺 key 直接 reject。
- **坐标系适配**：`VITE_COORDINATE_SOURCE`（默认 wgs84）——库内置 **WGS84↔GCJ02 互转**（境外坐标直返），`toAmapCoordinate`/`fromAmapCoordinate` 双向转换：**库存 WGS84，显示转 GCJ02**。
- **大量标记性能（MapContainer.vue 四板斧）**：①**自研网格聚合**——代码注释原话：高德 JS API 2.0 的 MarkerCluster 插件"**只认 setData 数据对象模式，无法托管已有 Marker 实例（setMarkers/构造传数组均不生效）**"，所以改为自研：`computePoiClusters` 按 zoom 动态 gridSize 网格分桶聚成气泡，`poiClusterMarkerMap` 增量同步；②**Marker 实例复用**——`poiMarkerMap` 按 poi.id 缓存，`syncPoiMarkerInstances` 只建新增/删 stale，**不全量重建**；③数据层 bounds 拉取 + limit 1200 + truncated 提示从源头限量；④`watch(visiblePoiList) → renderMarkers()` 单入口渲染。

#### ② 预埋追问逐条拆解

1. **Pinia store 设计？** 三 store 按"会话/数据/交互"切职责而非按页面切，跨组件共享（地图页选中 POI ↔ 列表 ↔ 详情）。setup 语法因为要写逻辑（planRouteAsync 合并多段路线），options 写不了；poi 用 `shallowRef` 是刻意的——上千条 POI 的深层响应式没有意义，只需要整个列表替换时触发。
2. **高德 JS API 加载时机？** 按需 + 单例 Promise + 幂等：第一次需要地图才插 script，并发调用共享同一个 Promise，重复调用先查 `window.AMap`。好处：不阻塞首屏（index.html 干净）、失败可控、多组件不会重复注入。
3. **地图组件性能（大量标记）？** 四板斧如上；核心故事是 **MarkerCluster 2.0 的坑**：插件模式托管不了已构造的 Marker 实例（自定义样式 DOM marker 必须自己建），最后自研网格聚合按 zoom 动态分桶——这是真踩过才能讲的细节。
4. **地图 key 管理？** 构建链：`.env`（本地）→ GitHub Secrets（CI）→ `import.meta.env` 构建期替换。认知加分点：**JS API key 本质是公开的**（会出现在每条地图请求 URL 里），防盗靠高德控制台的**域名白名单 + securityJsCode 安全密钥**配合，不是靠"保密"——所以放前端 env 是正确姿势，不是泄密。

#### 🎤 面试版总结

"Pinia 三个 store 按职责切：user 管会话和角色派生、poi 管数据——双列表设计，视口拉取和搜索结果分开存，用 shallowRef 避免上千条 POI 的深层响应式，另加一层实体缓存；map 管地图状态和路线规划状态机，多点路线是逐段调高德规划 API 再合并。高德 SDK 不放 index.html，按需动态加载：单例 Promise 保证并发只注入一次，幂等可重入。key 走 env 加 CI Secrets 构建期注入——JS key 本质是公开的，防盗靠域名白名单加安全密钥。大量标记的性能：自研了网格聚合——因为高德 2.0 的 MarkerCluster 插件托管不了自定义 Marker 实例，这是实际踩到的坑；再配合 Marker 按 id 复用增量更新、视口 bounds 拉取限量 1200，三层数量控制。"

#### ⚠️ 卡壳点

三 store 职责一句话（**user 会话 / poi 双列表+缓存 / map 地图+路线状态机**）；加载 = **按需动态 script + 单例 Promise 幂等**（不进 index.html）；性能王牌 = **自研网格聚合（MarkerCluster 2.0 托管不了 Marker 实例的坑）+ poiMarkerMap 增量复用 + bounds limit 1200**；key 认知——**JS key 本质公开，靠白名单+securityJsCode 防盗**。

### 27. UGC 治理怎么闭环（敏感词/举报）⭐（原 Q44 · 🟠P1）

#### ① 标准参考答案（基于真实代码）

**两层闭环：事前 DFA 脱敏 + 事后举报审核。**

**事前——SensitiveWordFilter（DFA 算法，143 行）**：
- 数据结构：嵌套 `Map<String,Object>`（key=字符，value=子节点 Map），终止标记 `END_FLAG="isEnd"`，替换符 `***`
- 初始化：`@PostConstruct` 从 `classpath:sensitive-words.txt` 加载（每行一词、# 注释；当前为演示词库 7 词：广告骚扰/刷单/诈骗/色情/赌博/毒品/违禁品）
- `clean(text)`：逐位置扫描，`matchEnd()` 沿 DFA 走取**最长命中**，命中追加 `***` 并跳到词尾继续；`containsSensitive(text)` 布尔版（严管场景"命中即拒绝"用）
- 复杂度：朴素 contains 是 O(词数×文本长)，DFA 预处理后**扫一遍文本 O(文本长)**——词库数千条时收益显著（类注释原文论证）
- **fail-open**：词库加载失败 log.warn 降级不过滤，不阻断启动——过滤是辅助层，不能变发布单点
- **接入点（grep 实证 4 个 ServiceImpl 共 11 处，全部入库前调用）**：

| 入口 | 调用位置 | 清洗字段 |
|---|---|---|
| POIShareServiceImpl | :148 / :276 | 分享内容 / 回复内容 |
| POIReviewServiceImpl | :87 | 评价内容 |
| UserRouteServiceImpl | :68-70 / :178-180 | 路线 title+summary+description（创建/更新双路径） |
| POIApplicationServiceImpl | :61 / :63 | 申报 name / description |

**事后——举报闭环（ContentReportServiceImpl + AdminContentReportServiceImpl）**：
- 用户举报分享/回复：防自举报（`validateTargetAuthor`）、**同目标 PENDING 去重**（重复举报拦截"等待管理员处理"）、reasonCode 范围校验、补充说明 ≤200 字、选"其他"必填说明、**内容快照 preview ≤300 字**（被举报内容删除后仍可审计）、冗余作者/POI 信息（列表页免联查）；双入口都有 `@OperationLog` 审计
- 管理端：`AdminContentReportController` 分页列表（keyword/targetType/status/reasonCode 筛选）+ 详情 + `reviewReport`
- 审核：落 `status`（PROCESSED/REJECTED）+ `reviewAction`（**ACTION_DELETE_TARGET 删除被举报内容 / ACTION_NONE 保留**）+ reviewNote + reviewedBy + reviewedAt——处理结果可追溯

#### ② 预埋追问逐条拆解

1. **敏感词 DFA 怎么工作？** 两阶段：建库 `insertWord` 逐字符建状态转移、末节点 isEnd=true；匹配 `clean` 逐位置起扫，`matchEnd` 沿树走取最长命中（处理"词中含词"），命中换 `***` 跳词尾。为什么 DFA：词库数千条时朴素 contains O(词数×文本长) 不可接受，DFA 预处理成状态机后线性扫一遍。
2. **为什么脱敏不拒绝？** UGC 场景命中率低，命中即拒绝误伤正常发布；脱敏保证入库合规又不阻断发布体验。需要严管的场景另有 `containsSensitive`（布尔拒绝）可用。fail-open 同理：词库挂了只是不过滤，不能让全站发不了内容——**辅助层不能变业务单点**，这与 AI 模块限流护栏的 fail-open 是同一个设计观。
3. **事前审核 + 事后举报怎么配合？** 事前拦"已知词"的机械过滤；事后兜**变体谐音、图片、语义类**漏网——用户举报 → 管理员带快照审核（证据已固定）→ 删内容或驳回，动作落库可审计。两层互补不是替代：DFA 管不住的正是举报存在的理由。
4. **词库怎么维护？** classpath 文件每行一词，重启加载。当前是演示词库（类注释明示生产应替换），生产两条路：换开源敏感词词库，或接第三方敏感词识别服务（顺带解决变体对抗）。
5. **图片审核（无）的局限？** 主动认：**没有图片审核**，图片仅靠人工举报兜底。这是已知局限（README 打磨方向也列了"内容审核策略升级"）；改进路线：发布图片异步送内容安全 API（如阿里云内容安全）审核 + 阻断/标记，成本可接受。

#### 🎤 面试版总结

"UGC 治理是两层闭环。事前：自研 DFA 敏感词过滤器——词库建成嵌套 Map 的状态机，扫描时取最长命中替换成星号，复杂度从词数乘文本长降到一遍线性扫；词库加载失败走 fail-open 只告警不阻断，因为过滤是辅助层不能变发布单点。接入覆盖四类 UGC 入口：分享、回复、评价、路线和地点申报的标题描述，共 12 处入库前清洗。事后：举报闭环——用户举报带去重、防自举报、内容快照 300 字固定证据，管理员审核后可以删除被举报内容或驳回，处理人时间动作全部落库可审计。为什么脱敏不拒绝？命中率低，拒绝误伤体验，严管场景另有布尔版可切换。图片审核目前没有，靠举报兜底，改进方向是接内容安全 API 异步审图。"

#### ⚠️ 卡壳点

两层闭环张口即出——**事前 DFA 脱敏（4 个 ServiceImpl 11 处）+ 事后举报（PENDING 去重 / 快照 300 字 / ACTION_DELETE_TARGET）**；数字：**最长命中 / *** / ≤200 字说明 / ≤300 字快照**；"脱敏不拒绝"理由落在"**辅助层不能变发布单点**"；图片审核主动认没有 + 给内容安全 API 路线。

### 28. 这个项目最大的短板是什么（原 Q48 · 🔴P0）

#### ① 标准参考答案（基于真实代码）

**答法三步：主动认 + 代价知情 + 有补救路线。首选真短板：测试覆盖不足。**

代码实证现状：后端 `src/test` 共 **11 个测试类**——SensitiveWordFilterTest、LoginRiskControlServiceImplTest、NotificationServiceImplTest、NotificationOutboxDispatcherServiceImplTest、AssistantGuardTest、AuthServiceImplTest、SystemConfigServiceImplTest、LocalFileStorageTest、GeoUtilsTest、AssistantAutoConfigureExclusionEnvironmentPostProcessorTest、ApplicationTests。覆盖集中在**工具类 + 最核心 Service 的单测**；但 **Controller 层、Repository 层、空间检索 RAG 三段式（bbox→Haversine→pgvector）没有集成测试**，前端 **0 测试**。CI 的 `mvn -B package` 默认会跑这些单测（pom 未配 skipTests），链路是通的，但覆盖面撑不起重构信心。

补救路线（按优先级）：①**空间检索 RAG 补集成测试**——Testcontainers 起 PG+PostGIS+pgvector 真库验证三段式召回，这是项目最核心、最怕回归的链路；②Outbox 投递/消费幂等补集成测试；③前端 Vitest 补三个 store 的状态机单测；估算 2-3 天可把核心链路覆盖起来。

次要短板一句话带过（README 打磨方向自证"有认知"）：文件存储在本地盘（已抽象 StorageClient 接口，可平替 S3）、权限是三级角色模型无资源级 RBAC、图片审核缺失、前端分包与首屏性能待优化。

#### ② 预埋追问逐条拆解

1. **测试覆盖（集成测试待补）？** 如实报数字：11 个单测类、覆盖哪些层、缺哪些层；关键句"CI 每次部署都会跑单测（package 默认生命周期），所以已有的是**拦门的**，缺的是**核心链路的回归保护**"；给 Testcontainers 方案（PG 系扩展用真容器，不起 mock）。
2. **伪流式？** 不当遮掩讲成偷懒：官方 SDK 流式 bug 的 **workaround（spring-ai#4790 / alibaba#1025 issue）**，call 整段返回后 30 字分块回放保住打字机体验；升级 SDK 修复后可切真流式，改造点只在响应组装层。短板认知题里这属于"外界约束 + 有方案"，不是设计缺陷。
3. **文件存储本地？** 单机量级够用 + 已做**存储抽象**（StorageClient 接口，LocalFileStorage 是实现），迁 S3/OSS 是加实现类不改业务代码；顺带认"上传文件清理自动化待做"（README 已列）。
4. **权限模型粗？** USER/ADMIN/SUPER_ADMIN 三级 + Service 层资源归属校验（如举报的 validateTargetAuthor、分享删除校验作者）；没有细粒度 RBAC，当前量级不需要，量级上来先加资源级 ownership 校验中间层。
5. **多久能补？** 给排序和时间：RAG 集成测试 1-2 天（最高优先、最怕回归）→ Outbox 幂等测试 0.5-1 天 → 前端 store 单测 0.5 天。体现的是**评估和规划能力**，这才是这题真正考的。

#### 🎤 面试版总结

"最大的短板是测试覆盖。后端有 11 个单测类，覆盖了工具类和最核心的几个 Service，CI 部署前也会跑它们；但空间检索 RAG 这条最核心的链路、Controller 和 Repository 层没有集成测试，前端完全没有测试——重构信心撑不起来。补救我排了优先级：先用 Testcontainers 起 PG 加 PostGIS 加 pgvector 真库，给三段式检索补集成测试，这最怕回归；然后是 Outbox 幂等，最后补前端 store 单测，大概两三天能把核心链路罩住。其他短板我也有认知：文件在本地盘但做了存储抽象可平替 S3、权限是三级模型、图片审核缺失靠举报兜底。这些我都清楚代价和改进路径。"

#### ⚠️ 卡壳点

第一句定调"**最大短板 = 测试覆盖**"（数字背熟：**11 个单测类 / Controller 与 RAG 集测缺失 / 前端 0**）；答法三步 **主动认 + 代价知情 + 补救路线（Testcontainers + 2-3 天）**；伪流式答成"**官方 bug 的 workaround + 有升级路径**"不是设计缺陷；其他短板一句话带过证明全局有认知——**切忌遮掩或过度自黑**。

## R9 · 实战复盘（线上事故，最强一手素材）

### 31. 线上 500 事故复盘：Flyway 静默失效（2026-08-29 实战 · 🔴P0 ⭐⭐⭐⭐⭐）

**考察**：线上故障排查方法论（信号→定位→根因链→止血→根治→预防）+ 对 Spring Boot 自动配置机制的理解深度。**这是一手实战案例，市面上几乎没人踩过 SB4 这个坑，含金量远超八股。**

#### ① 标准参考答案（真实事故，全部有据可查）

**现象**：2026-08-29 晚 CI 自动部署后，https://map.jieai.shop 登录及所有涉及 users 表的 API 全部 500。日志关键行：`column u1_0.profile_visibility does not exist`——PG 报列不存在。

**排查路径（三步）**：
1. SQL 错误 → 直查库：`\d users` 确认 `profile_visibility` 列确实缺失。但实体有字段、`V2__add_user_profile_visibility.sql` 迁移脚本也在 jar 里——**为什么没生效？**
2. 查 `flyway_schema_history` 表：**不存在**。真相浮出：Flyway 引入一个月以来**从未运行过**，不是这次失败，是一直静默瘫痪。
3. 为什么静默？解开 jar 看依赖列表：只有 `flyway-core`，**没有 `spring-boot-flyway` 模块**——SB4 根因。

**根因链（五环叠加，一环都不少）**：
1. **SB4 自动配置模块化拆分**：Spring Boot 4 把按技术的自动配置拆成独立模块（`spring-boot-flyway` 等），只有引 `spring-boot-starter-flyway` 才会把模块带上 classpath。项目引的是裸 `flyway-core` → `FlywayAutoConfiguration` 根本不在 classpath → Boot 条件装配直接不装 Flyway——**零日志、零报错、零警告**（不是"条件不满足"，是自动配置类压根不存在，沉默得理直气壮）；
2. **外部遗留配置冒充迁移器**：VPS 上 4 月份遗留的 `config/application-prod.properties`（Spring Boot 外部化配置：jar 旁 config/ 目录**优先级高于 jar 内**）里 `ddl-auto=update` 赢得优先级，Hibernate update 一直在"好心"补结构；
3. **update 生成不了 DEFAULT**：新实体字段写 `private Short profileVisibility = 0;`——**Java 字段初始值是对象层语义，不参与 DDL 生成**，update 产出的 DDL 是 `add column ... smallint not null`（无 DEFAULT）；
4. **PG 拒绝**：users 表有存量行，给存量行加无 DEFAULT 的 NOT NULL 列 → `ERROR: column "profile_visibility" of relation "users" contains null values`；
5. **异常被吞、带病启动**：Hibernate SchemaMigrator 的默认 ExceptionHandler 是 `ExceptionHandlerLoggedImpl`（haltOnError=false），DDL 失败只打 WARN 日志不中止启动——进程健康启动、接口全 500。旧版本之所以没事：旧 jar 里实体还没这个字段。

**止血（5 分钟）**：手工 `ALTER TABLE users ADD COLUMN profile_visibility SMALLINT NOT NULL DEFAULT 0;` → 服务恢复。

**根治（四个 commit 内改动）**：
1. `pom.xml` 补 `spring-boot-starter-flyway`（附事故注释，防止后人再删）；
2. V2 脚本防御式改造：包 `DO $$ BEGIN IF EXISTS(...users) THEN ALTER ... DEFAULT 0 END IF; END $$;`——**表存在才 ALTER**（Flyway 先于 Hibernate 执行，全新空库时 users 还没建，裸 ALTER 会让启动失败）+ **必须带 DEFAULT**（注释里写明事故教训）；
3. **外部配置归档收编**：VPS 遗留文件改名 `.bak`，缺的两项配置（forward-headers-strategy、multipart 10MB）收编进仓库 `application.properties`——消灭配置漂移源；
4. **deploy-backend.sh 升级**：`sleep 3 + is-active` → 轮询 `/actuator/health`（90s 超时）+ **失败自动回滚**软链到上一版；CI 加一步从仓库同步 deploy 脚本（消灭脚本漂移）。

**修复验证**：下次部署后 `flyway_schema_history` 出现三行（baseline 0 / V1 / V2）全 success=t；health UP；线上接口 200。此后 prod 的 `ddl-auto=validate` 只校验不改表，**结构变更唯一入口 = V{n} 脚本**。

#### ② 预埋追问逐条拆解

1. **为什么 Flyway 瘫痪一个月没发现？** 静默失败的本质：它没有报错信号，监控只看进程存活（is-active）不看业务健康。这正是把部署检查升级为 health 探针的理由——**进程存活 ≠ 业务健康**。诚实补刀：如果当时 Flyway 有跑，V2（无 DEFAULT 版本）也会在存量库上失败，但会失败得"更响"。
2. **update 模式为什么加不出 DEFAULT？** Java 字段初始化 `= 0` 是 new 对象时的默认值，不参与 DDL 生成；DDL 默认值需要迁移脚本或 columnDefinition。顺带表明立场：update 生成的 DDL 不可控（加列无默认、删列不敢做），**生产本就不该用它管结构**，这次等于"错的工具在替正确的工具背锅"。
3. **为什么 Hibernate 吞了 DDL 异常还能启动？** SchemaMigrator 默认 `ExceptionHandlerLoggedImpl` + haltOnError=false——update 的语义是"尽力而为"，失败打 WARN 继续。这在"开发期改表"场景合理，在"生产启动"场景就是带病放行。
4. **配置优先级怎么回事？** Spring Boot 外部化配置顺序：**jar 同目录 config/ 子目录 > jar 内 classpath**。VPS 那份 4 月遗留文件一直压着 jar 内配置。教训：外部配置是漂移源，要么收编进仓库+环境变量，要么明确归档。
5. **如果是全新空库会炸吗？** 不会——update 先建全表（含新列，无存量行约束），反而无事。事故是"**存量数据 + 无 DEFAULT 的 NOT NULL**"组合拳，这类"只在有数据的库上炸"的问题最阴险，本地空库测试测不出来。
6. **怎么保证不再发生？** 四道防线：结构变更唯一入口 V{n}（validate 模式兜底）；部署 health 探针拦带病启动；部署脚本随代码走（CI 同步，无手工漂移）；迁移脚本防御式写法（幂等 + 注释记录教训）。

#### 🎤 面试版总结

"上个月我处理过一次线上全站 500。现象是部署后所有涉及用户表的接口报列不存在。三步排查：查库确认列真缺失；查 flyway_schema_history 表——根本不存在，说明 Flyway 引入一个月从没运行过；解开 jar 找原因。根因是 Spring Boot 4 把自动配置按技术拆成了独立模块，我引的是裸 flyway-core，Flyway 自动配置类根本不在 classpath，它就静默瘫痪——零日志零报错。这段时间结构一直是 VPS 上遗留的 ddl-auto=update 在偷偷管，新版本给用户表加无默认值的非空列，有存量数据被 PG 拒绝，Hibernate 又默认吞掉 DDL 异常继续启动，于是进程健康、接口全 500。止血是手工加列；根治四件事：补 starter、迁移脚本防御式改造带默认值、外部配置收编进仓库消灭漂移、部署脚本升级成健康探针加失败自动回滚。验证是 history 表三行全成功，从此结构变更唯一入口就是版本化脚本。这个事故我最大的收获是：静默失败比报错失败可怕得多，防线要建在'没有信号'的地方。"

#### ⚠️ 卡壳点

根因链**五环顺序别乱**（依赖缺失→静默瘫痪→update 冒充→无 DEFAULT 被拒→吞异常带病启动）；第一句话先说现象再说排查三步；两个专有名词别说错——`spring-boot-starter-flyway`（不是"忘了开配置"）、`ExceptionHandlerLoggedImpl`（不是"try-catch 吞了"）；结尾金句"**静默失败比报错失败可怕，防线建在没有信号的地方**"；追问②记得补"生产本就不该用 update 管结构"。
